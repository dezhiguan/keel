# R1 任务编号先规范再调用工具

## 目标

DF-0017 第 20 版沙箱 136 通过、1 失败、6 跳过。唯一失败是测试把整句和编号写成小写并期望 PASS，岗位仍用大小写敏感的 `DF-\d+` 提取，实际 BLOCKED。生成提示把该正则当成正确示例，又要求“开发者要测试就必须改测试”，模型因此只追加用例、不同步实现。

本规格只改元智能体生成契约和交付前静态检查。不提高累计二十轮上限，不重置额度，不修改已生成的业务仓库。

## 规则

- 岗位若用正则提取 `DF-` 加数字的任务编号，必须在同一表达式中把原文或每个匹配结果转成大写，再作为 `jobId` 调用工具，并与返回记录的 `id` / `jobId` 比较。
- 只加 `re.IGNORECASE` 不能通过静态检查。大小写不同的同一编号视为同一任务。
- 同一候选里新增的测试必须被这份实现满足。编号规范化、动作级否定、必需工具各保持一处，不为同一规则继续堆叠另一套正则。
- 正常限制性查询可以查；否定一个动作后紧接另一个肯定写操作必须 BLOCKED。
- 没有这种编号正则的岗位不受此检查影响。

## 修改文件

`agents/meta-agent/candidate.py`、`agents/meta-agent/tests/test_candidate.py`。

## 验收

- 敏感提取、以及只加 `IGNORECASE` 的提取，在静态检查被拒绝。
- 对原文 `upper()` 后再匹配，或匹配后对每个结果 `upper()`，可以通过该项检查。
- 现有无编号正则的候选测试仍通过。本地只跑元智能体测试，不部署、不提交页面反馈。
