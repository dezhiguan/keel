# 元智能体第二版：逻辑模型、版本化技能与双实例

## 目标与边界

按正式手写智能体项目维护 meta-agent。保留受控 workflow、CREATE 生产范围、现有权限和人工发布关口；本轮不扩展 CHANGE、知识库或自主发布。完成基线、实现、评测与发布三个阶段，最终部署两个就绪实例。

## 阶段一：基线

- 保存当前发布版本、镜像、52 条 ACTIVE 用例及各标签分数，不覆盖历史记录。
- 模型名称属于接入契约：评分器使用用例声明的期望模型，旧用例缺省保留第一版具体模型预期；第二版用例声明逻辑模型。除该字段外保持原有判断及门槛 minScore=0.99、maxRegression=0.02。
- 先跑网关适配候选，再跑技能候选，保留相同核心用例和各维度对比。用例扩展单独记录，不以增加分母掩盖核心能力退步。

## 阶段二：实现

- manifest 显式 kind=workflow，模型使用已发布逻辑入口 chat-default；所有调用仍走 ctx.llm，生成项目继承逻辑入口。
- 将代码生成、评审、评测扩充指令纳入 prompts 声明；按职责拆分候选生成/校验、评审和交付模块，app/workflow 保持入口与编排职责。兼容现有内部导入，避免无关重写。
- 增加人工维护的 keel-project-development v1 技能（说明、示例、回归用例），在代码生成阶段显式加载并使用，平台授权与 manifest 锁定一致，不授予额外工具权限。技能加载失败必须显式失败，不静默忽略。
- 技能与步骤提示词各司其职；原有权限、审计、SHA 比较、审批和门禁由代码执行。
- 双实例共用现有持久卷与交付锁；明确当前单节点 local volume 限制，原子写状态，SDK 本地追踪/审计文件按 Pod 隔离。验证跨实例恢复和重复交付。

## 阶段三：发布与验收

- 本地及可信环境运行元智能体回归、技能专项和发布配置检查。
- 提交推送触发现有 CI/CD，等待镜像构建与 rollout 成功；平台评测绑定真实镜像及提示词版本，通过门禁后形成第二版发布记录，保留第一版可回滚证据。
- 验证两个 Ready 实例、逻辑请求/实际模型/路由证据、技能加载、核心52条完整评测、分维度回归、跨实例状态和交付互斥。
- 线上失败保留原始证据，修复后重新提交、部署并复测，不把预检或部分评分当作门禁通过。

## 双实例核实后的共享 SDK 范围

SDK 的 runs.json 原先只用临时文件替换，多个进程读改写会丢失其他运行；resume 也先读再写，存在重复消费。必须同步修改 sdk-python/keel/runs.py 与 asgi.py：文件锁保护索引更新，原子消费恢复令牌，增加跨进程竞争测试。无契约字段变化。

## 核实后的发布接口补齐

现有注册接口拒绝已开通的同名智能体，不能用它更新第二版模型、提示词与技能声明。新增 PUT /agents/{name}/candidate（先改 console-api.openapi.yaml，再同步类型）：有写权限的归属用户提交 env、expectedHash、manifest，只能更新未发布v0候选；身份、权限、运行地址、预算、护栏和门禁阈值不变，技能须已有授权，活动评测期间拒绝修改。已发布v1快照不覆盖。ReleaseService 按最大数字版本计算下一个发布版本，避免较新的v0候选把第二版错误计算为v1。范围增加相应服务、控制器、测试和生成的 API 类型。

本接口供代码项目运维使用，不改变现有页面交互；已对照10月14日原型和UI清单，现有评测/发布入口继续使用。第二版数据集按网关候选、技能候选分别保存，保留旧52条定义；新增生成预览与成功评审用例，覆盖全部声明提示词。生成预览只接受评测流量，不执行Git或文件交付。

候选配置更新后，旧评测不得被绑定到新配置：发布在创建快照前检查评测创建时间不早于最新候选时间。已经绑定过不可变版本的运行继续指向该原版本，不拿最新候选冒充旧版实测。

## 历史清单漂移的受控对齐

线上核实发现旧注册清单仅有两个工具和两个审计字段，运行镜像已经有scaffold.deliver、job_id及0.99/0.02门禁，不能把旧清单当作第二版完整快照。候选接口新增可选reconcileRuntime（缺省false）：仅真实可写ADMIN可显式发起，从原先登记地址读取真实manifest（元智能体使用既有bridge身份）；只可对齐该运行端已有的本地工具、审计字段和不降低的门禁。原工具权限和审计字段不能移除或变化，共享/其他智能体工具不能经此授权；门禁同时不得低于当前生产评测的实际门槛。身份、运行地址、预算、护栏等仍按原边界拒绝变更。只写未发布v0，旧v1快照及实测记录保留原样，历史漂移单独记录。先改契约及生成类型，增加授权、运行证据和门禁回归测试，再经CI部署该能力后执行对齐。

双Pod实测发现SDK恢复流程在创建真实agent.resume span之前用随机ID初始化Context，响应和模型账单因此不能对应Langfuse实际链路。恢复流程须先创建span并使用其真实trace_id初始化Context/LLM客户端，保持事件和重新暂停检查点一致；增加final/suspend/error三条路径回归，纳入元智能体CI。此修复不改变协议字段或恢复授权。

候选写入须遵循现有数据库manifest_hash VARCHAR(64)，保存无前缀SHA-256十六进制值。真实PostgreSQL回归覆盖候选更新、已发布快照不变和相同清单重试；候选时间使用写入时clock_timestamp()，避免长事务中now()早于已发布快照而读回旧版本。
