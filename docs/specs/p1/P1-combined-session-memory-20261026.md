# 摘要与事实合并维护（第二阶段）

依据原异步化设计第二阶段；保留第一阶段异步热路径、两个独立任务及其 CAS/租约/来源校验。只改后台调度和模型输出编排，不改事实状态机和上下文硬上限。

- 可选 claim `combine:true`，同一事务以 SKIP LOCKED 领取同 agent/env/owner/session 的另一类型任务，响应可选 `companion`。无对应任务继续单任务，旧客户端行为保持。
- SDK `KEEL_MEMORY_COMBINED_ENABLED=true` 显式启用，默认关闭；同会话两个合法租约才能组合。摘要只取一个完整连续 chunk，事实保持原批次，不扩张游标。组合输入大于7000估算 token 时在付费前改为分别执行。
- 一次 `purpose=memory` 输出 `{summary:string,facts:{operations,ignoredSourceIds}}`。输出上限1600，保留既有调用/费用上限。摘要引用与事实操作分别校验，分别 complete/fail；成功一侧不因另一侧失败回滚，不允许摘要成功掩盖事实失败。
- 共享调用费用、token、calls 只记到主任务，companion 记0并共享后台trace；两者都记录各自task、原始范围和结果。崩溃仍按各自租约保守预留，最多3次领取，不因新用户轮次重置失败预算。
- 有效结果提交后失败侧独立重试；JSON根损坏/超时两侧失败。取消、删除、过期、CAS 冲突继续依赖第一阶段权威提交检查。组合失败不在同一轮偷偷增加付费调用。
- 正式发布 SDK 后锁定助理版本/hash，staging先保持combined关闭作同版本对照；质量/费用通过后开启并执行第一、二阶段回归、2/4QPS各300秒、后台收敛。实际费用必须使用网关已结算记录，同等处理范围对比，缺失费用记未知。未达标保留分开维护并报告原因。

首轮SDK30真实30对小批次：分开29/30、合并29/30，合并费用+4.43%，未通过。保留失败，压缩重复的摘要提示规则，共用事实提示；明确撤销不得提取为新预算/日期值。含糊的独立“是/确认/第二个”在共享事实校验中禁止成为任意新操作，仍可标记无事实原文推进cursor。重测质量、结算费用及两阶段功能后再决定开启。

SDK31事实30/30但小批次重试后均费+8.70%，未通过。SDK32增加收益门槛：按同一摘要完整前缀与相同facts批次估算分开输入总量与组合输入，至少节省512估算token才合并；否则付费前分别维护。摘要无事实也必须保留交流原文引用。验收同时纳入30小批次和30长重叠批次，分别列费用，不能以混合均值掩盖小批次退化。该估算是选路保守策略，不替代实际账单证明。

最终staging每副本8worker，日预算110元保持。两阶段实现及全部失败/复测证据见[实施验收报告](../../design/记忆摘要与事实合并维护实施验收报告-20261026.html)。保留小批次费用波动、撤销表示偏差、trace回读限制及首轮4QPS四例未闭环内部错误，不宣称全量推广门禁全部通过。
