# R3-5k 评审阶段的有界岗位功能修复

## 背景与目标

`DF-0002` 已用完两次基础设施模板刷新，沙箱通过，但可见用例不能执行且岗位逻辑固定返回 H1 阻塞。现有 `retry` 在 `WAITING_REVIEW` 仅能刷新模板，无法把功能问题交回元智能体修正。允许一次评审阶段功能修复：旧 SHA → 元智能体重写候选 → 新 SHA → 重跑隔离沙箱 → 人工 PR 评审。

## 依赖与范围

- 依赖 R3-5、R3-5h、R3-5j；无外部 API 新增。
- `POST /devflow/jobs/{jobId}/retry` 在两次模板刷新耗尽后，且当前沙箱 PASS 时，最多进行一次岗位功能修复；读取旧提交的受信快照作为不可信模型输入。
- 服务端记录 `reviewRepairRounds`，清除旧人工/模型评审及沙箱通过标志。新候选必须产生新 SHA 并完整重跑沙箱。
- 元智能体交付的总提交轮次边界为原先五轮加一次评审修复；该修复失败后不自动放宽测试或发布门禁。
- 修复执行中遇到基础设施瞬时错误可重试同一轮；真实测试失败后停止。

## 界面对齐

生产线任务详情 `WAITING_REVIEW` 且模板刷新为 2/2 时，显示一次「修复岗位功能」；说明单独的 `reviewRepairRounds` 计数，不把它计作模板刷新。更新 `ui-checklist.md`。

## 验收

- 当前精确 SHA 的沙箱 PASS 才能申请；旧 SHA、PR 头、任务仓库标记不一致时拒绝。
- 最多一次，生成新 SHA 且新沙箱 PASS 才能重返 `WAITING_REVIEW`。
- 原有人工 PR review、S4 评审全部失效，必须针对新 SHA 重做。
- 候选功能测试失败时停止，不能把旧沙箱结果复用为通过。
