# R3-5n 候选仓库 SDK 版本锁与 CI 刷新

## 线上证据

DF-0002 第九次候选 `4d63873aeb895280b80a5c77c9d83023d0c157f8` 的隔离沙箱通过，但 GitHub Actions 两次 `verify` 均在读取 `.keel-sdk-version` 时失败。仓库快照含安装 SDK 的工作流，却没有版本锁文件。旧交付目录被复用时，交付逻辑没有补齐 `keel new` 后来新增的文件。当前任务已用完两次基础设施刷新与一次 S4 修复，控制台无法再刷新这次基础设施缺陷。

## 修复

- 元智能体在每次候选交付时补齐缺失的 `.keel-sdk-version`，使用与 `keel new` 一致的 SDK 版本；已有版本锁保持不变。文件随精确提交进入 Git 仓库。
- 第九次 S4 修复候选允许一次第十次 CI 配置刷新。只复用上一版岗位代码，更新交付脚手架，再对新 SHA 重跑沙箱、GitHub CI、真人与 S4 评审。不能继承旧 SHA 的审批，也不能借此绕过失败的岗位测试。
- 第十次沙箱失败时停止自动修复。可信门禁、合并与发布继续由原有条件控制。

## 验收

- 对缺版本文件的旧交付目录重新交付，快照包含 `.keel-sdk-version=1.0.0`；已有锁文件不被改写。
- 第九次 S4 修复后可执行一次 CI 刷新，第十次不能再次刷新；候选代码保持一致，所有旧评审证据清空。
- 线上新 SHA 的 GitHub Actions `verify` 通过后，才重新核验真人评审和运行 S4。
