# R3-5l 候选 PR 校验与 staging 可信门禁分离

## 故障与目标

`DF-0002` 的公开候选 PR 在 GitHub Actions 中运行 `uvicorn app:app` 和 `keel gate --env staging`。岗位尚未注册、开通 staging 资源或完成人工评审；受管 SDK 启动需要薄网关、审计和服务身份配置，因此 PR 校验在门禁前失败。公开 PR 可修改候选代码，不能把平台长期密钥交给该工作流。让候选 PR 的无密钥校验能真实运行，同时保留评审后独立的可信 staging 门禁及隐藏考题。

## 范围

- 生成的 PR 工作流只做源码检出、SDK 安装、锁定依赖安装、单元测试、评分函数加载与构建；成功状态仅表示候选预检通过，不得命名为 staging 门禁通过。
- 不在公开候选 PR 的 Actions 中注入薄网关、审计、CI 身份或平台服务私钥；不在 PR 推送时自动注册、发布。
- `STAGING_READY` 后才在平台控制的环境运行可见及隐藏考题门禁；仍须绑定人工批准的精确候选 SHA、不可变镜像和已开通的 staging Deployment。不得放宽现有 `MetaAgentExecution.recordStagingGate` 校验。
- 当前 PR 需要产生新 SHA 并重跑沙箱；任何旧的人工与模型评审证据失效。
- 对 `DF-0002` 这类已用完两次模板刷新及一次功能修复的执行，允许恰好一次专门的 CI 模板修正（第 7 次候选交付）。只保留上个精确 SHA 的岗位代码，重建可信工作流；失败的连接/交付可重试同一轮，沙箱真实失败不可越过。第 7 次沙箱通过后不得再刷新。
- 第 7 次复测发现平台生成的 `test_smoke.py` 把沙箱目录名 `repo` 错当作 manifest 名称。仅当可信沙箱报告的当前 SHA 精确匹配这条断言失败时，允许第 8 次模板勘误交付；岗位代码保持不变，重新完整跑沙箱。第 8 次真实失败后停止。

## 界面与验收

任务详情沿用沙箱、评审及门禁字段；界面文案须区分预检与 staging 门禁。PR Actions 无密钥预检可成功启动且不会请求运行时平台密钥；`DF-0002` 新 SHA 的沙箱重新通过。未有真实人工 PR 审批时，`runCodeReview` 和 staging 门禁仍拒绝。门禁不通过时不能进入 H4 或发布。

## 2026-10-17 轮次调整

岗位代码修复上限由三轮提高到五轮后，独立计数的两次模板刷新对应第 6、7 次候选，评审阶段功能修复对应第 8 次，候选 CI 修复对应第 9 次，可信冒烟勘误对应第 10 次。上述 `DF-0002` 的第 7/8 次记录属于历史实际执行，不改写审计。
