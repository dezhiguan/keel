# R3-6 研发候选的可信部署流水线

依据 P1-26 S5/S6 和控制台原型的门禁、发布动作。当前独立仓库只有无密钥预检，S4 后无法从页面继续部署。

## 范围

- 任务详情在 S4 通过后提供 staging 流水线入口；H4 受保护合并后提供 prod 门禁与发布入口，显示状态和 CI 链接。
- 由底座仓库的固定 GitHub workflow 执行。候选仓库的工作流不持有平台或 CI 长期密钥。
- 可信 CI 身份由服务器生成并保存在专用 Secret；仅 CI 路由可以读取经 S4/H3 绑定的精确代码快照、登记对应岗位、同步其提示词、回报该提交的门禁和发布。
- 构建不可变镜像摘要；部署使用 agents 命名空间、环境独立 Service/Deployment/Secret、精确 SHA 标签及两个副本。运行资源仍由现有 LifecycleService 开通。
- 在可信代码中运行可见和隐藏评测，采用标准 decision 比较器，不导入候选评分代码。隐藏内容不进入日志、候选代码或对话。
- staging 通过后才能申请 H4；prod 针对合并 SHA 重新构建和实测，通过后登记 prod 并发布。S7 仍须真实七天观察。
- 不修改已生成的岗位代码。接口新增均保持 keel/v1 兼容。
- 修复评审后的开发迭代预算：一次已授权的岗位/S4 修复会话最多运行五次沙箱，绝对上限二十次；既有仅运行一次就失败的评审修复可继续同一会话。每个新 SHA 均重新过测试和审批。
- 工具调用按请求环境读取已登记 manifest 和资源，不能与最新登记环境直接比较。H4 后、正式 prod 登记前的合并提交预览允许沿用已批准的 staging 能力；该例外必须同时存在 RELEASING 状态、staging 门禁和当前任务的 H4 批准证据。

## 契约与验证

先更新 console-api 的 pipeline 字段和启动路由。CI 路由按身份、任务、环境和精确 SHA 校验；非 CI 与旧 SHA 均拒绝。验证审批/阶段规则、快照路径处理、实际得分失败会阻止发布、控制台类型检查及线上两岗位流水线。
