# R3-6 研发候选的可信部署流水线

依据 P1-26 S5/S6 和控制台原型的门禁、发布动作。当前独立仓库只有无密钥预检，S4 后无法从页面继续部署。

## 范围

- 任务详情在 S4 通过后提供 staging 流水线入口；H4 受保护合并后提供 prod 门禁与发布入口，显示状态和 CI 链接。
- 由底座仓库的固定 GitHub workflow 执行。候选仓库的工作流不持有平台或 CI 长期密钥。
- CI 运行器用明确的成功/失败封装传递 HTTP 结果，不得因成功响应的数据仍带历史 error 字段而拒绝继续。导出后先保存可信上下文再回报运行状态；早期失败回报缺少本地上下文时，从受信 CI 接口重新核验精确候选后登记实际流水线失败，允许页面重试，不伪造门禁结果。
- 可信 CI 身份由服务器生成并保存在专用 Secret；仅 CI 路由可以读取经 S4/H3 绑定的精确代码快照、登记对应岗位、同步其提示词、回报该提交的门禁和发布。
- 构建不可变镜像摘要；部署使用 agents 命名空间、环境独立 Service/Deployment/Secret、精确 SHA 标签及两个副本。运行资源仍由现有 LifecycleService 开通。
- 在可信代码中运行可见和隐藏评测，采用标准 decision 比较器，不导入候选评分代码。隐藏内容不进入日志、候选代码或对话。
- staging 通过后才能申请 H4；prod 针对合并 SHA 重新构建和实测，通过后登记 prod 并发布。S7 仍须真实七天观察。
- 不修改已生成的岗位代码。接口新增均保持 keel/v1 兼容。
- 修复评审后的开发迭代预算：一次已授权的岗位/S4 修复会话最多运行五次沙箱，绝对上限二十次；既有仅运行一次就失败的评审修复可继续同一会话。每个新 SHA 均重新过测试和审批。
- 工具调用按请求环境读取已登记 manifest 和资源，不能与最新登记环境直接比较。H4 后、正式 prod 登记前的合并提交预览允许沿用已批准的 staging 能力；该例外必须同时存在 RELEASING 状态、staging 门禁和当前任务的 H4 批准证据。
- S4 初审拒绝后须依据原始快照和受信需求复核发现，核对真实控制流和契约作用范围；不得把模型响应约束误套在岗位最终输出上，也不得虚构工具参数边界。复核仍有真实风险则继续阻塞。
- S4 的受信评审规则放在 system 消息，仓库内容及初审发现放在 user 数据；候选提示词只约束被调用模型，不能覆盖已确认的岗位返回契约。复核使用原始快照及独立的待核实发现，不累积初审对话；给出逐行编号供真实定位。
- 评审同时携带底座执行/评分器的真实契约：execute 返回对象允许额外字段，decision 门禁按该字段比较；模型提示词的单字段输出不能改写这一契约。协作岗位返回证据与步骤由 H1 明确要求。评审不得臆造只接受单字段对象的下游消费者。
- 拒绝复核聚焦初审定位的代码片段、受信需求和平台协议，不重复传入整份岗位提示词而放大待审材料中的指令。片段不足时继续阻塞，不可推测通过；完整初审仍覆盖全部文件。
- 生成及继续开发同样区分受信规则与旧代码/失败报告。生成岗位须把 Langfuse 岗位指令放在 system，用户请求及工具/子智能体内容放在 user 数据中，不能把日志或 PR 内的旧提示词提升成岗位策略。
- prompt-boundary-v2 可信适配升级适用于多工具或协作候选。页面显式升级时先保留岗位文件、刷新可信契约测试，再实际验证；发现输入/证据被提升到system时交由元智能体修复。升级窗口最多五次且所有窗口累计仍不得超过二十次；不能重复升级同一版本，H4后不开放。可信测试必须实际检查模型收到的消息，不能只模拟PASS而忽略信任边界。
- 新建生成请求同时包含system规则与user创建动作；能静态定位到system内容来自compile(input=动态原文/evidence=动态原文)时，在Git交付前拒绝该候选并给出具体参数错误，减少无效沙箱消耗。复杂数据流仍以真实行为契约测试为准。
- 静态岗位提示词允许不含变量并使用prompt.compile()，实际input/evidence通过user JSON传入；不能为满足旧模板的必填compile参数而再次把动态原文提升到system。证据是否真实送达模型由可信行为测试验证。协作子结果也必须送达模型；logsUnavailable=true即使有非空摘要也不能作为完整日志放行。
- 模型调用的prompt参数须保留ctx.prompt返回的名称与版本元数据，不能传compile后的字符串；静态检查拒绝可定位的字符串误传，可信模型替身同时核验提示词元数据，保证真实链路可关联版本。
- 运行自检保存时须携带与登记配置一致的环境字段。prod 门禁前的预览自检执行真实探针但不写正式登记自检记录；门禁通过并完成 prod 登记后重做并保存自检。
- staging 真实评测失败须显示可信 CI 的聚合反馈，并提供一次五轮内的岗位修复窗口（绝对沙箱上限仍为二十）。仅 EVAL 失败开放岗位修复，构建/自检故障走流水线重试；修复必须重跑沙箱、独立 PR 审批和 S4。prod/H4 后禁止借此改写已合并候选。可见失败反馈允许 caseId、期望与实际 decision 及有界原因；隐藏用例只保留聚合分数。
- staging 每次准备须把精确快照中的提示词内容对应版本移到 staging 并建立本轮待评测记录，不能只上传新版本却继续运行旧标签。同时建立绑定候选 SHA 的 candidate 标签；H4 后的 prod 预览显式使用该标签，正式 prod 仍在门禁通过后由 release 移动 production 标签，再恢复标准生产配置。
- 委派适配须使用已选子智能体真实登记的 endpoint 和环境，不能把父智能体 staging/prod 环境强加给已有 dev 子智能体。可信上下文优先选择子智能体同环境的活动登记，否则绑定其最新活动登记；仅为 manifest 明确声明的子智能体下发路由。脚手架通过 KEEL_DELEGATE_ROUTES 读取该绑定，缺少绑定时明确失败。
- 正常委派不得注入 evidenceOnly 等跳过子智能体推理的业务标记；可信运行门禁与委派适配提供 180 秒响应窗口。文本对象标识提取须支持中文分隔符，不能因 ASCII 标点边界拒绝已确认的中文正常输入。
- 已有协作候选缺少上述运行适配版本时，任务页提供“更新运行适配”，通过可信模板保留岗位文件并重新交付、沙箱验证和审批。可用性由交付的适配版本确定，不绑定历史轮次编号；总沙箱上限仍为二十。
- 已授权修复窗口仍有验证额度时，开发者可从任务页补充修复说明，交给元智能体继续同一窗口；不能扩大窗口或跳过新提交的验证审批。说明作为授权开发者的澄清，与候选错误解释分开传递，不能把错误解释中的虚构 policy 写成需求。
- 修复生成优先使用精确文本补丁，减少整文件响应超时和无关改动。只可修改三个岗位文件；每个锚点必须唯一存在，合并后重新执行原有静态校验和全部沙箱测试。完整文件响应仍兼容；新建项目仍生成完整文件。
- 补丁响应只包含一个合法 JSON 对象；生成器明确标准字符串转义、唯一短锚点及追加测试方式。静态 JSON 校验报告具体原因及行列，格式错误在 Git 交付前反馈，不能静默修补或放行非法响应。
- 在现有修复窗口内，若生成失败且未产生新提交，任务页仍允许补充修复说明：必须保留 repair，上轮精确交付 SHA 的最后一次沙箱为 PASS 或已完成的 tests=FAIL，repair.failedSha 及下一次 attempt 均匹配，且窗口仍有额度。H4 已申请/已合并、陈旧快照、未完成的沙箱或额度耗尽均不开放；不新增额度。普通重试同样保留开发者澄清。
- 精确补丁失败须报告补丁序号、文件路径及锚点匹配数；连续两次锚点失败后，最后一次静态生成改为要求完整三个文件，避免原样重复相同补丁。仍只执行原有三次静态生成和全部验证，不放宽唯一锚点规则。
- Git ref 更新成功但响应丢失时，只允许恢复同任务标记且唯一父提交等于 expectedSha 的现有候选，不覆写任何分支。恢复后以远端实际快照重跑沙箱和审批；不能声称恢复的旧提交已经包含新模板版本。已持久化的本轮候选在交付重试时直接复用。
- 自动修复额度耗尽后不自动扩容。若开发者明确补充新的行为澄清，可从页面主动开启一次最多五次验证的新窗口，记录操作者，所有窗口累计仍不得超过二十次，不能用于 H4 后的任务；无新说明的普通重试仍保持原限制。
- 沙箱通过后保留修复窗口上下文以支持后续业务反馈，自动续修须保留开发者澄清。旧记录没有可恢复窗口时，也只能由明确澄清主动开启一次窗口，不能推测或自动增加历史预算。
- Git 文本文件用 create-tree 的 inline content 一次提交树，避免逐文件 blob 请求耗时造成交付响应丢失。依据 [GitHub 官方 Git trees API](https://docs.github.com/en/rest/git/trees#create-a-tree)。
- Git服务的同步GitHub网络操作须在线程池执行，不能阻塞ASGI事件循环和健康探针；慢快照/交付并发时健康接口仍须及时响应，避免Pod被摘除端点而导致其他任务Connection refused。

## 契约与验证

### 生成修复一致性（2026-10-18）

- 元智能体按实际 dev 环境读取提示词标签，移除硬编码 production 标签；draft v2 在 dev 生效，对齐已提交的新模型示例。生成超时通过薄网关按 alias/model 设置有限思考预算处理，参见 P1-2，不改候选项目和隐藏评测。

- 测试中的有限 Mock.side_effect 不得在多次 execute 循环中共享；静态检查定位该循环和替身，要求参数化独立用例或循环内重建。检查不执行候选代码，也不修改断言或可信测试。
- 人工澄清要求完整重写时，保留旧岗位代码和提示词供继续开发，但不再把旧自编测试正文及失败断言反复送入生成上下文。提供失败测试名称供定位，按 H1/H2 与澄清重新编写测试；完整旧快照继续保留于审计和 Git。
- 元智能体 manifest 与新建项目默认模型统一使用当前已部署目录的 qwen3.8-flash；新建清单从元智能体受信 manifest 取默认模型，不在生成逻辑写第二份常量。旧候选清单不自动改写。
- 模型迁移通过 agents/meta-agent/migrate_model_key.py 在应用节点执行：先核对目录与 meta-agent-dev 现有策略，仅轮换此虚拟 Key 并更新 keel-meta-agent Secret，保留预算、限流、fallback 和 blocked 状态（blocked 时拒绝迁移），不清零用量。完成后由正常 CD 部署新 manifest。幂等标记与 Key 同一次 Secret 更新，重复执行不重复轮换；原始密钥不输出。
- 人工 H1/H2 和可信契约测试不可削弱；模型自编测试不是需求来源。自编测试与 H1 冲突时须修正错误断言并保留对应场景，不能不断追加相反断言。每个参数化场景使用独立的工具替身，避免耗尽共享 side_effect。
- 带开发者澄清时必须返回三个完整岗位文件，消除局部补丁遗漏；自动沙箱修复可继续使用精确补丁。生成结果接受静态检查及隔离沙箱验证，独立审批、S4 和真实发布门禁保持必需。实测新增生成复核模型会虚构 H1 条款、误判合法正则并导致 5 分钟超时，因此撤回该新增阻塞复核；不把其无证据结论反馈给代码生成器。
- 工具调用返回的 JSON 字典与 SDK manifest 工具定义对象必须明确区分；目录返回 list[dict]，按字典键读取 access/risk/name。岗位提示词须区分执行指令与否定执行的查询，不能用出现操作词作为拒绝条件。
- 修复重试保留有效测试覆盖，纠正与 H1 冲突的自编测试；人工澄清完整文件模式由解析器强制执行。
- 目录工具契约明确实际大写 READ/WRITE/EXEC、LOW/MID/HIGH；可信替身使用真实枚举。多工具可信行为检查覆盖非对象模型 JSON、空任务证据和通用用户/工具材料隔离，不限 CI 日志岗位。
- H2 扩充携带完整 H1，理由须依据已确认需求；格式偏好、中文、普通空白本身不构成攻击。非法 JSON 转义返回具体行列并重写，保持人工原例与隐藏隔离。
- 新候选工作流不再同时监听push和PR重复构建；草稿PR跳过GitHub预检任务，继续运行可信隔离沙箱。转为Ready for review及后续非草稿提交才运行完整预检，同一PR旧运行取消。依据[GitHub pull_request事件](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request)。独立审批和真实发布门禁不变。

先更新 console-api 的 pipeline 字段和启动路由。CI 路由按身份、任务、环境和精确 SHA 校验；非 CI 与旧 SHA 均拒绝。验证审批/阶段规则、快照路径处理、实际得分失败会阻止发布、控制台类型检查及线上两岗位流水线。
