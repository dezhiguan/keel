# R3-5o 候选岗位 SDK 契约修复

## 目标与证据

DF-0002 第十次候选 `dfbbfcb5db5bdc2d58b5e727a7966191ca090bf0` 沙箱与 GitHub Actions 均通过，但正常执行路径不符合真实 SDK：`ctx.manifest.spec.tools` 的条目是模型对象，不能调用 `.get()`；不带 `tools=` 的 `ctx.llm.chat()` 返回字符串，不能调用 `.get("content")`。候选测试把这两处错误模拟为字典，造成假阳性。候选还在所有返回路径固定 `status=BLOCKED`，把已通过的 H1 当作未确认。不能让该提交获得真人批准、进入 S4 或门禁。

## 边界

- 扩展元智能体静态校验，拒绝对 manifest 工具对象使用字典 `.get()`，以及对 `ctx.llm.chat()` 的字符串结果使用 `.get()`；测试不应把这两个 SDK 值伪装为字典。岗位所有返回路径固定 `status=BLOCKED` 也拒绝。生成提示明确 SDK 真实类型与 H1 已确认状态。
- 在第十次候选已通过沙箱、前述修复轮次已用完时，允许一次专门的 SDK 契约修复。服务端沿用精确提交快照，把实际问题作为诊断交给元智能体，生成第十一次候选；不可复用旧岗位代码。
- 第十一次候选必须重跑沙箱、GitHub CI、真人审查和 S4。清空旧 SHA 的人工及模型评审证据。若新候选仍失败，停止自动修复；不改动受信 manifest、工具授权、H1/H2 或评分门槛。
- 无新接口或跨语言字段；控制台按已有轮次和状态显示一次“修复 SDK 调用”入口。

## 验收

- 静态校验能拒绝本次两种误用，且接受真实 SDK 访问方式和字符串模型结果。
- 第十次候选可触发一次修复，第十一次不能再触发；沙箱失败不会进入评审。
- 线上新 SHA 的运行时契约、沙箱和 CI 均通过后，才请非作者真人评审。
