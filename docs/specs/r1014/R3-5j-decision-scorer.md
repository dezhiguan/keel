# R3-5j 研发岗位可见用例的确定性评分

## 目标

元智能体已交付的 `evals/scorers.py` 仍是占位注释，`keel gate` 在加载评分函数时立即失败。H2 人工用例的 `expected.decision` 是可核对的结论文本；生成的岗位结果是 JSON，结论位于 `output.decision`。交付一个严格的默认评分函数，让门禁能执行并能真实拦截不符合用例的候选。

## 范围

- 修改 `agents/meta-agent/workflow.py` 的可信交付模板，让有岗位候选的项目写入 `evals/scorers.py`。
- 只评分人提供的 `expected.decision` 与岗位 JSON 结果的 `output.decision`；Unicode 规范化与空白差异可忽略，其他内容必须完全相同。结构错误、缺字段、候选答非所问均为 0 分。
- 模型不能生成、修改这个评分函数。评分函数不调用模型、网络或文件。
- 现有 `DF-0002` PR 必须产生新精确 SHA 并重新走沙箱与评审；模板上线不会静默修改旧 PR。

## 界面对齐

沿用任务详情已有的候选 SHA、沙箱记录、门禁分数。无新增页面字段。

## 验收

- `load_scorers` 找到恰好一个评分函数；精确结论为 1，答非所问、非法 JSON、缺字段为 0。
- 当前候选固定输出 H1 阻塞时，28 条可见用例不会被误判为全通过。
- 新候选评分文件出现在交付 PR 中；完整 staging 门禁仍须在隔离可信环境运行，并依赖真实部署及隐藏考题证据。
