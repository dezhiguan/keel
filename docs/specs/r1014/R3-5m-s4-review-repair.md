# R3-5m S4 模型评审失败后的单轮候选修复

## 故障与目标

`DF-0002` 的第 8 次候选提交 `17471f83317d0c9801132748df640aa24aa53e04` 已通过隔离沙箱、无密钥预检，并获得不同作者的真人 PR 批准。S4 模型代码评审发现 `role.py` 和提示词把两个工具的风险写死为 MEDIUM/HIGH，而受信工具目录、H1 确认的 manifest 和设计文档均为 LOW；评审未通过，现有评审阶段功能修复轮次已用完。候选正常路径还固定返回 H1 阻塞，尚不能进入可信门禁。

增加一次仅由**失败的 S4 模型评审**触发的修复轮次，使元智能体根据受信 manifest 的工具定义和模型评审意见重写岗位代码，再对新提交完整重跑沙箱、预检、真人 PR 评审和 S4。不能改写受信工具目录来迎合候选代码，也不能把失败评审伪装成通过。

## 依赖与边界

- 依赖 R3-5k、R3-5l。无新外部接口；现有 `POST /devflow/jobs/{jobId}/retry` 复用。`DevflowExecution` 只新增可选 `s4RepairRounds`，先改 OpenAPI 契约，再改服务端和控制台。
- 仅在 `WAITING_REVIEW`、当前精确 SHA 的沙箱为 PASS、`humanReview.approved=true`、`modelReview.approved=false` 且存在 HIGH/MID finding 时，允许一次 S4 修复。服务端核对 PR head 与当前 SHA。`s4RepairRounds` 从 0 到 1；达到上限后不得再次修复。
- 修复报告只能取服务端已保存的结构化模型评审 findings。交给元智能体时标为不可信诊断数据；受信 `draft.manifest.spec.tools` 和工具目录为风险、访问级别与审批要求的唯一事实来源。禁止因模型评审的错误推断而擅自抬高或降低工具风险。
- 元智能体必须生成新的岗位代码提交，不复用第 8 次岗位代码；新提交必须重跑隔离沙箱。生成失败或真实测试失败即停止，不绕过边界。重置旧 SHA 的人工/模型评审证据，并要求真人重新批准新 SHA。
- 候选代码静态校验失败后的同一生成调用，应把上一版完整候选和具体错误作为下一轮模型消息，使模型能针对该版本修正；仅记录错误而丢失上一版候选会反复生成同类错误。不能截断候选；超过 1MB 的异常响应直接报错。维持最多三次模型生成，仍不合格则失败，不放宽 `{{input}}`、`{{evidence}}` 与真实工具证据传递等校验。
- 静态校验必须按 Keel SDK 的 `Prompt.compile` 语义识别 `{{ input }}` 与 `{{ evidence }}`（可带空格），并接受从 `ctx.prompt("role")` 获取的提示词对象使用其他局部变量名或带类型标注的赋值。点号和未闭合的 `{{` 等 SDK 无法替换的占位符必须明确报错，不能把未展开的风险值交给岗位模型。
- S4 修复候选已用 compare-and-swap 推送到原任务的 `draft` 分支后，`git.pr.open` 应复用同一任务仓库里 head 为 `draft`、base 为 `main` 的现有开放 PR，即使真人已将其标记为可评审。新提交仍须重新跑沙箱、预检、当前 SHA 的真人审批及 S4，不能继承旧评审。若 Git PR 操作暂时失败，同一修复轮次可从任务本地交付检查点复用已验证候选和已推送 SHA；不得重新生成并覆盖该提交。
- `candidate-preflight` 仍只做无密钥预检。只有新 SHA 的真人 PR 批准、S4 通过、staging 资源和部署就绪后，才可运行可信可见/隐藏门禁；分数不达标继续拦截合并与发布。

## 界面与验收

- 任务详情在上述条件下显示一次「修复 S4 评审问题」，并展示独立的 `s4RepairRounds` 计数。按钮不对草稿、未批准、S4 已通过或已用完轮次的候选开放。
- `DF-0002` 的第 9 次候选必须有新 SHA，沙箱报告绑定该 SHA；扩展五轮基础修复后的执行若已经用了第 9～10 次 CI 模板修复，则专项修复最多到第 11 次。旧真人评审和 S4 结果不能被新候选继承。
- 用注册表 LOW 的 `devflow.catalog.search`、`devflow.stage.report` 验证生成提示包含受信风险定义；不应把候选硬编码的 MEDIUM/HIGH 当成受信事实。
- S4 修复通过也只进入 `STAGING_READY`，不自动合并、注册或发布。
