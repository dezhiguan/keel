# 日成本、总成本与历史账单对账

## 用户确认的范围

- 运行总览智能体表将「成本」改为「日成本」，增加「总成本」。日成本为上海时区当天 00:00 至今，总成本为全部历史已结算账单。
- 智能体管理卡片及详情使用同一费用口径。费用只统计 SETTLED 且 costCny 非空的尝试；待计费条数另外展示。
- 总览上方模型成本跟随时间筛选，累计模型花费始终读取全部账单。
- 从完整网关账单重建各历史日汇总，允许晚结算修正已封账日期，累计数字不能依赖可能漏记的旧汇总。
- 测试通过后提交、推送，等待 CD 成功再验证线上；无法访问的步骤须如实记录。

## 正确性要求

- 以完整网关账单为统一费用来源，不把 Redis 每日预算计数当账本。
- 从同一份账单计算所选窗口和累计，日成本跨午夜重置而总成本不重置。
- 每条尝试按 attemptId 唯一；降级的不同尝试分别计费，同 requestId 的调用数去重。
- 历史全量读取失败或达到分页上限必须报错，不能发布截断后的总成本；不估算遗失账单，不把缺失当零。
- 历史重建可重复执行，不累加重复费用；晚结算可修正历史日；全部无调用的今天为已知零。
- 不修改业务账单、预算、审计，不发起模型调用来测试成本。

## 线上根因与修复补充

2026-10-27 实测：keel-llm Secret 缺失 JDBC 三项，网关只读最多 5000 条的 Redis SpendLog，导致历史账单被截断。昨天助手的真实 Redis 已结算额为 80.601330，保留的逐次记录仅约 13.80。已私下备份现有 Redis 数据及历史日汇总，不包含数据库密码。

- 生产清单强制 JDBC 配置，建立独立 keel_llm 数据库；启动时幂等导入仍保留的近期账单，后续调用持续落库。
- V2 增加独立的 llm_daily_recovery 日结算凭据表及只读历史视图。凭据来自已备份的真实已结算额或既有历史日账，不来自预算限额、预留金额或估算。恢复投影只补「已确认日结算额 - 同日同别名现有逐次账单费用」的正差，防止重复计费。
- 恢复行标注 daily-recovery / recovered-daily-settlement，无 requestId、模型、tokens 或 trace，不能冒充逐次模型调用。归属不可恢复的历史费用单独记为历史未分配费用，不归给某个真实智能体。
- 日成本、总成本和完整自然日时间窗包含已确认恢复额。若 24h 等窗口切过只有日精度的恢复记录，模型成本显示不可精确拆分，而不是伪造小时金额。
- scripts/recover-cost-ledger.py 在应用节点读取 Secret 到内存、备份日账、幂等导入原始账单和已确认日结算凭据，并配置 JDBC；不修改预算，不估算逐次明细，不输出凭据。

- 补充验证：网络恢复后模型网关/使用量/分页 HTTP 测试通过；第一轮 CI/CD 已成功。独立数据库已建立，JDBC 已配置；V1/V2 SQL 在真实 PostgreSQL 的隔离事务中验证，恢复差额会随明细补齐而减少，合计不重复，测试事务已回滚。下一轮发布包含生产必需配置及恢复视图。

- 日结算恢复没有逐次调用及 token 详情。重建历史费用时保留此前已观察到的调用/token 数，不将仅金额恢复行的零详情覆盖掉已知历史统计。

线上恢复结果：原始记录保留/导入 5023 条，74 条日结算凭据（含零金额依据）；网关账单视图已确认总额 103.304090 元，助手已确认总额 91.059455 元。重复导入以 attemptId 和 day/alias 去重，恢复差额随原始明细自动扣减；不恢复缺失模型/token/小时信息。
