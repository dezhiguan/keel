01目标与范围

一句话目标：新智能体只写业务逻辑、填一份 agent.yaml，一天内接入底座；旧智能体逐个迁移，删掉各自重复的追踪、审计、评测、质量代码。

本期要交付

  • 4 个新服务：keel-gateway、keel-server、keel-audit、keel-console
  • 2 套 SDK：Python keel-sdk（含 CLI、keel-lite、keel-gate），Java keel-spring-boot-starter
  • 接入 Langfuse Cloud 日本节点（追踪、评测、质量、提示词），自研薄网关 keel-llm（模型调用、虚拟 Key、人民币日预算）
  • 5 份契约 keel/v1：manifest、调用协议、追踪属性、审计事件、评测集
  • 5 个脚手架模板：chat-rag、tool-agent、graph-agent、supervisor、java-spring
  • 现有智能体迁移：askdb、offshore-wind、careermate，rag-forge 作为共享服务接入

本期不做

  • keel-gateway 完整版的协议适配、流式脱敏、灰度（放 P3）
  • Dify 部署和智能客服上线（放 P3）
  • 多租户计费、对外 SaaS 化
  • 自研追踪存储、自研评测平台：直接用 Langfuse
  • 自建 Langfuse、另买观测节点

一次调用经过哪些组件

以"运维总控把任务委派给 askdb 和 offshore-wind"为例：

1前端 → keel-gatewayPOST /agents/ops-copilot/v1/invoke，带 auth-gateway 签发的 JWT
2keel-gatewayJWKS 验签（用户 token 的 aud 是 keel-api）→ 按 roles / scopes 判断能否调用 ops-copilot → Redis 扣配额、占并发位 → 生成根 traceparent → Token Exchange 换成 aud=ops-copilot 的 token → 转发
3ops-copilot（SDK）轻量校验 JWT → 入口护栏 → 业务代码 ctx.llm 调 薄网关 做规划
4ops-copilot → 子智能体ctx.delegate：Token Exchange 换票，注入 traceparent，K8s 内网直连 askdb、offshore-wind 的 /v1/invoke（不经网关）
5子智能体调 rag-forge 检索、调 薄网关 生成；各自的 span 通过 OTLP/HTTP 异步上报 Langfuse
6高风险工具SDK 调 keel-server 创建审批单并挂起 → 审批人批准 → 继续执行；同步写 keel-audit
7keel-gatewaySSE 透传回前端；结束后释放并发位，经 RocketMQ 写一条 invoke 审计事件
8keel-console追踪页调 keel-server，keel-server 调 Langfuse API 组装协作图，叠加审计和审批信息

04服务清单：哪些要新建

结论：新建 4 个服务 + 2 套 SDK，部署 2 个开源组件，复用 3 个现有服务。控制面采用"模块化单体"，先合在 keel-server 一个服务里，包边界按模块划清，以后需要时再拆。

组件结论形态职责为什么这样定
keel-gateway新建Java 服务 ×2外部流量入口：动态路由、JWT 准入、配额与并发、换票（aud=keel-api → 目标智能体）、SSE 透传、根 span、调用级审计高并发、长连接、要独立扩缩容，必须单独部署
keel-server新建Java 服务 ×2注册中心、资源开通、在线探测与对账、工具注册与生命周期、审批流、发布记录、控制台 API（聚合 Langfuse / 薄网关 / Prometheus）这些模块数据互相关联、流量小，合成一个服务最省运维；按包隔离，后续可把审批或对账拆出去
keel-audit新建Java 服务 ×2审计写入（同步 + MQ 异步）、哈希链、查询、导出、归档安全要求不同：独立数据库账号、只追加；高风险动作要同步写入，不能被控制台的故障拖累
keel-console新建Vue 静态站点 + Nginx控制台页面前后端分离，API 全部走 keel-server
keel-sdk（Python）新建pip 包 keel-sdk智能体运行时 + keel CLI + keel-lite + keel-gate一个包装好就全有，开发者只装一次
keel-spring-boot-starter新建Maven 依赖Java 智能体运行时careermate、研发智能体都是 Spring Boot
keel-llm自研2 副本，放现有应用节点薄网关OpenAI 兼容、虚拟 Key、人民币日预算、降级
Langfuse云端日本节点追踪、评测、质量、提示词2026-10-04 已实测。追踪数据在 AWS 东京
auth-gateway复用现有签发 JWT、JWKS、Token Exchange、委托授权（consent）需改造 4 处 客户端注册 API、按 aud 配置 scopes、业务角色 claim、智能体密钥托管，见 第 15 节
rag-forge少量改造现有知识检索，作为共享服务接入加 OTel Agent、指标标签、模型调用走 薄网关、审计同步（见第 09 节）
ai-multi-agent-dev-platform改造现有拆成 prd-agent、test-gen、dev-copilot升级 Boot 3.2→3.5、Java 17→21，引入 starter
keel-gate 不是服务：它是 Python SDK 里的一个命令（keel gate），在 CI 流水线里运行，跑完把结论回写 keel-server，不常驻。keel-lite 也不是服务：它是本地开发时 keel dev 起的单进程替身，用 SQLite 模拟审计和审批。

过滤器顺序（数字越小越先执行）
  • -200 RootSpanFilter：最先执行，保证被拦截的请求也有 trace
  • -100 JwtAuthFilter → -90 AgentAccessFilter
  • -80 QuotaFilter → -70 ConcurrencyLimiter
  • -60 TokenExchangeClient（放在配额之后，被限流的请求不换票）
  • 0 路由转发 + SsePassthroughFilter
  • InvokeAuditFilter 在 doFinally 里发事件，成功、失败、取消都会记
轻量版不做
  • 协议适配、流式脱敏、灰度、熔断（P3）

08关键流程实现

1CLI本地校验 agent.yaml（JSON Schema），打包 manifest + evals/seed.jsonl 发给 keel-server
2keel-server · registry校验名称唯一、owner 存在、声明的工具和知识库都存在且有权限；写 agent、agent_version
3provisioning生成 RSA 密钥对，公钥挂到 /agents/{name}/jwks.json → 在 auth-gateway 注册 OAuth 客户端（client_id=智能体名、allowed_audiences、token-exchange 授权、scopes）→ 薄网关 建虚拟 Key → 写 K8s Secret keel-{name}（KEEL_CLIENT_PRIVATE_KEY、KEEL_LLM_KEY、KEEL_LLM_BASE_URL、LANGFUSE_PUBLIC_KEY、LANGFUSE_SECRET_KEY、LANGFUSE_HOST）→ 导入 Langfuse 数据集；每步写 agent_resource，失败按逆序回收
4自检等 Pod 就绪 → 调 /v1/health、/v1/manifest → 发 5 条协议自检请求（带评测标记）→ 查 Langfuse 是否收到 span → 查高风险工具是否绑定审批策略
5完成状态 REGISTERED；写 route_snapshot（网关此时只对 staging 开放）；写 config.change 审计；返回自检报告
1SDK · ToolInvoker检查工具在 manifest 中声明且授权 → 读风险等级和审批策略
2SDK → keel-serverPOST /api/v1/approvals，payload 只传摘要和 digest；SSE 推 step {name:"approval", status:"pending"}
3keel-server按策略找审批人，推送企业微信 / 控制台待办；同步写 approval · pending 审计
4SDK 挂起存现场拿到 checkpoint_ref → 置 agent_run 为 SUSPENDED → 发 event: suspend {run_id, reason:"approval", ref, deadline, resume_token} → SSE 流正常关闭，网关借此释放并发位。等待期间计为"人工等待"，不计入智能体耗时；超过 deadline 置 EXPIRED
5审批人决策控制台或企业微信回调 POST /api/v1/approvals/{id}/decision；keel-server 同步写 approval · approved 审计，再调智能体的 POST /v1/runs/{run_id}/resume
6恢复SDK 按 checkpoint_ref 还原现场 → 重新换票（原换票 token 600 秒必然已过期；用户会话也失效的改用 /oauth/delegation-token，两者都没有则返回 RUN_RESUME_DENIED）→ 执行工具 → 同步写 tool.call · approved 审计（写失败则不执行）→ 新的 SSE 流接着跑完
审批只是挂起的一种。底座把「等人」统一成运行生命周期：suspend.reason 有 approval（等批准）、input_required（等用户回答）、handoff（转人工）三种，共用同一套待办、通知、超时和审计，智能体不用各自建后台。边界：底座管账（run 状态、谁有权决定、截止时间、审计、恢复入口），智能体管现场（状态怎么序列化、怎么接着跑）。底座永远不决定下一步做什么，只在人做完决定后把现场原样递回去。v1 底座只存 checkpoint_ref 字符串，不存现场内容——askdb 继续用自带的 LangGraph checkpointer。详见 docs/specs/p0/P0-1a-run-lifecycle.md。
1CI单测通过后运行 keel gate --env prod
2keel gate用 Langfuse SDK 对数据集跑实验：逐条调用候选版本的 /v1/invoke（带 X-Keel-Eval-Run）→ 大模型裁判 + 代码评分器打分
3对比读当前 prod 版本最近一次实验分数，按用例 tags 逐维度对比：总分 < minScore 或任一维度退步 > maxRegression → 失败
4回写POST /api/v1/gate-results，CI 按退出码决定是否继续
5keel releasekeel-server 校验 gate_run_id 已通过 → 提示词打 production 标签 → 更新 agent_version、路由 → 审计

写业务逻辑核心工作

from keel import Agent, Context
agent = Agent.from_manifest("agent.yaml")

@agent.entry
async def handle(req, ctx: Context):
    diff  = await ctx.tools.call("git.pr.diff", pr_url=req.input["pr_url"])
    rules = await ctx.knowledge.search("dev-standards", diff.summary, top_k=8)
    review = await ctx.llm.chat(messages=review_prompt(diff, rules))
    await ctx.tools.call("git.pr.comment", pr_url=req.input["pr_url"], body=review.text)
    return ctx.final(review, citations=rules.citations)

app = agent.asgi()

13开发规范

契约

  • 改契约先改 contracts/，Java 模型和 Python pydantic 模型由它生成
  • 契约带版本 keel/v1；新增字段必须可选；删除字段要升 v2，平台同时兼容两个小版本
  • 契约测试：SDK 和 starter 都要跑同一套 contracts/tests 用例

错误码

  • 格式 {模块}_{原因}，如 GW_QUOTA_EXCEEDED、TOOL_NOT_GRANTED、TOOL_RETIRED、APPROVAL_REJECTED
  • 错误体统一 {code, message, trace_id, retryable}
  • SSE 中出错发 event: error，不直接断连

日志与追踪

  • 所有日志带 trace_id、agent
  • span 属性不放原文，原文只按审计白名单记录
  • Keel 服务自身的服务级追踪进 SkyWalking，智能体语义追踪进 Langfuse

测试

3没有业务角色token 只有单值 platform_role（ADMIN / KB_EDITOR / KB_VIEWER / USER）manifest 里的 auth.roles: [ops_engineer] 无从判断加 roles 多值 claim（来自新表 user_roles）；过渡期先用 scopes agent:{name}:invoke 控制

另外两点，不阻塞开工：① token 有效期：访问 token 900 秒、换票 token 600 秒。研发总控这类跑几十分钟、要等人工审批的流程，不能一直拿着用户 token，改用 auth-gateway 已有的委托授权（用户授权一次 → /oauth/delegation-token 签发 principal_type=agent 的 token）；普通调用由 SDK 在 token 过期前 60 秒自动重新换票。② 换票 token 的 act 是字符串，多级委派时会被覆盖，看不到完整链路。Keel 的委派链靠追踪（keel.parent_agent）和审计记录，不依赖 act；以后可以改成 RFC 8693 的嵌套 act。
换票规则落到客户端配置上：auth-gateway 要求"被换的 token 的 aud"和"要换成的 aud"都在客户端的 allowed_audiences 里。所以 keel-gateway 客户端要允许 keel-api + 全部智能体；ops-copilot 客户端要允许 ops-copilot + manifest 里 delegates 的 askdb、offshore-wind + ragforge-api。这张表由 keel-server 根据 manifest 自动生成，注册、改 delegates 时同步给 auth-gateway。
