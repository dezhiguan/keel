Keel 龙骨

智能体平台底座：只建一次，所有智能体复用

龙骨是船底那根纵梁。船上装什么货各不相同，但每条船都靠它承重。Keel 对智能体也是这个角色：鉴权、模型调用、知识检索、链路追踪、审计、评测、质量监控、工具审批、人工介入与恢复都由底座承担，每个智能体只写自己的业务逻辑。

02

设计原则与总体架构

这五条原则决定底座能不能真正被复用。有一条没做到，新智能体最后都会绕开底座，自己再写一套。

P1

智能体只写业务

追踪、审计、评测、鉴权、模型调用由 SDK 自动完成，业务代码里不出现上报逻辑。

P2

协议优先于代码库

Python 和 Java 共用的是 HTTP + SSE + 统一事件格式，SDK 只是协议的薄封装。换语言、换框架、换成 Dify 都能接入。

P3

上报不阻塞业务

追踪异步批量上报，失败先写本地缓冲再重试。高风险审计例外：写不进去就拒绝执行。

P4

评测是门禁，不是报表

分数低于阈值自动阻止发布。评测集随代码版本化，改提示词也要过门禁。

P5

复用已有，薄处自研

auth-gateway、rag-forge 直接成为底座组件。追踪、评测、质量用 Langfuse Cloud（日本节点）。模型网关自研一层薄代理：OpenAI 兼容、虚拟 Key、按人民币计的日预算和降级。Keel 再做这两边覆盖不了的治理，并把它们串成一个整体。

03

控制台演示

Keel 控制台的交互原型，左侧菜单可以点击切换。所有智能体（包括用 Dify 做的客服）在同一套页面里看追踪、评测、质量和审计。链路追踪页演示了一次多智能体调用：运维总控把任务并行委派给 askdb 和 offshore-wind，可以在协作图、泳道时间线、调用树三种视图间切换，点任意节点看详情。正式控制台的链路追踪先是可筛选、可分页的调用列表，点一行进入这样的详情；单智能体调用只有泳道和调用树，见控制台原型 docs/console/Keel-控制台前端.html。审计页的记录可以点开，审批卡片可以点批准或驳回。

不是在控制台放两个跳转按钮。集成分三层：开发者日常看的、日常做的操作都在 Keel 里完成，只有深入排查时才带着上下文跳过去。

层做什么具体做法
① 运行时打通
开发者看不见		智能体不直接感知 薄网关 和 Langfuse，由 SDK 在背后接好ctx.llm 的地址指向 薄网关，带上该智能体的虚拟 Key，以及 agent、trace_id、session_id 等 metadata；每次模型调用由 SDK 记成 Langfuse 的 generation，挂在当前 trace 下。薄网关 自带的 Langfuse 回调关闭，避免重复记录

底座怎么知道智能体上线、下线了

以注册中心为准，再用运行时信号核对：主动登记决定"应该有哪些"，运行时探测确认"实际在跑哪些"，定期对账找出两边的差异。

登记与探测

  • 主动登记：keel register → 已注册；keel release 过门禁 → 上线；keel retire → 已下线。Key 只在注册时发放，没登记的智能体调不了模型、报不了追踪
  • K8s 探测（k3s 上的智能体）：Deployment 打标签 keel.io/agent，注册中心 watch 这些 Pod，就绪探针用 /v1/health；再调 /v1/manifest 核对运行版本和登记版本
  • SDK 心跳（函数计算、定时任务、集群外服务）：启动时上报实例，每 15 秒续约，45 秒无心跳记为离线
  • API 探活（Dify 应用）：注册中心定时调一次 Dify API

每 5 分钟对账

  • 登记了、在运行、有流量 → 正常
  • 登记了、不在运行 → 离线，告警并通知负责人，保留 Key 和配置
  • 在运行、很久没有流量 → 僵尸，提示是否下线
  • 在运行、没登记 → 未登记，告警（有人绕过了流程）
  • 已下线、仍在运行 → 下线不彻底，告警并确认 Key 已吊销
  • 流量从 Langfuse（按 agent 数 trace）和 薄网关（按虚拟 Key 数调用）两边取
要不要用 Nacos：Java 智能体多、服务发现本来就用 Nacos 时，可以让 Nacos 承担"在不在线"这一层；manifest、状态机、Key 发放这些治理数据仍放在 Keel 注册中心。现在的规模直接用 K8s watch 就够了，不必多引入一个组件。

自研 keel-gateway：先做轻量版

选自研不选 Higress：模型代理已经交给 薄网关，入口网关的核心（按注册中心路由、Keel 审计契约、渠道协议适配）本质是业务逻辑，用 Java 写比写 Wasm 插件好开发、好调试，资源占用也小。基于 Spring Cloud Gateway，JWT 验签、Redis 限流、SSE 都有现成支持。

模块轻量版（P2，约 2～3 周）完整版（P3 起按需）
路由/agents/{name}/v1/invoke 按注册中心的 endpoint 转发；路由表本地缓存，变更推送，不重启；只放行"上线"状态按用户或比例灰度到新版本
鉴权准入JWKS 验签（Spring Security 资源服务器，不自己解析 token），要求 aud=keel-api，按 manifest 里的角色准入；Token Exchange 换成目标智能体 aud 的 token（用户 token 只有一个 aud，必须换票）开放 API 的 API Key；企业微信、钉钉回调验签
配额用户、组织、智能体三个维度的 Redis 令牌桶；并发会话数上限（SSE 是长连接，只限 QPS 不够）日调用上限、按组织的套餐
流式SSE 透传：关缓冲、长超时、心跳；客户端断开时取消上游请求输出流式 PII 脱敏（滑动缓冲，跨 token 块识别）
护栏长度限制；其余仍在 SDK输入注入检测、敏感词前移到网关
追踪审计生成根 traceparent 并上报根 span；每次调用（含被拦截的）写一条 invoke 审计事件，经 RocketMQ 异步入库按智能体的首 token 时间、拦截次数看板
协议适配—企业微信、钉钉、Dify 转成标准 /v1/invoke
韧性每个智能体单独超时；两副本熔断，智能体挂了返回友好提示或转人工；只对非流式幂等请求重试
和 SDK 的分工：网关上线后，JWT 准入、用户配额、调用级审计移到网关；SDK 保留轻量 JWT 校验作为双保险，工具审计、审批、接地校验、ctx.llm 都不变。配一条 K8s NetworkPolicy，智能体只接受来自网关的流量，防止绕过网关直接调智能体。TLS 证书、WAF 这类通用流量管理交给前面的 Nginx 或阿里云 SLB，网关只做智能体特有的事。

追踪设计要点
  • 三个服务、一个 trace：委派时通过 W3C traceparent 传播，子智能体不需要知道自己被谁编排

  • generation 的 input / output 上报到 Langfuse，链路页再从 observation 读回展示

from keel.eval import scorer, Score

@scorer("fault_type_match")
def fault_type_match(case, output) -> Score:
    got = output.meta.get("fault_type")
    ok = got == case.expected["fault_type"]
    return Score(value=1.0 if ok else 0.0, reason=f"判定为 {got}")

  • 智能体提供：评测用例、领域评分函数

agent = Agent.from_manifest("agent.yaml")

@agent.tool("alarm_query")                 # 风险等级、审批策略从 manifest 读取
def alarm_query(turbine_id: str) -> list[dict]:
    return scada.query_alarms(turbine_id)

@agent.entry
async def handle(req, ctx: Context):
    with ctx.step("route"):                # 自定义步骤，自动生成 span
        p = await ctx.prompt("route")      # 按环境取 staging / production 标签的版本，带缓存和本地兜底
        route = await ctx.llm.chat("qwen-flash", messages=p.compile(question=req.text), prompt=p)
    docs = await ctx.knowledge.search("fault-manual", req.text, top_k=5)
    p = await ctx.prompt("answer")
    answer = await ctx.llm.chat(messages=p.compile(question=req.text, docs=docs.text, route=route),
                                prompt=p)  # 传 prompt=p，链路上才能看到这次用的是哪一版
    return ctx.final(answer, citations=docs.citations)

app = agent.asgi()    # 自动挂载 /v1/invoke /v1/health /v1/manifest

提示词怎么管

底座要管提示词，原因有三条：改提示词和改代码一样会让效果退步，必须过门禁；业务方要能自己改，不能每次找开发发版；出了问题要能从一条链路查到当时用的是哪一版。存储、版本、diff、调试台直接用 Langfuse，Keel 补上它在我们这套部署下缺的四件事。

缺口原因Keel 的做法
跨环境同步dev、staging、prod 是三个 Langfuse 项目，提示词只在本项目内可见，标签也是编辑只发生在 staging 项目。keel release 门禁通过后，keel-server 把门禁实测用的那一版复制到 prod 项目并打 production 标签。两边版本号不同，按内容哈希对应，记进发布记录
谁能改Hobby 套餐网页用户只有 2 个，业务方进不了 Langfuse；保护标签要 Enterprise控制台"提示词"页按智能体负责人授权编辑，keel-server 代写 Langfuse。prod 的 production 标签只由 keel-server 改，有人在 Langfuse 里手动挪了，PromptDriftJob 告警并记审计
改动要过门禁Langfuse 改完立刻生效，不管效果在 staging 生效即触发回归实验；发布时校验门禁实测的提示词版本 = 当前 staging 版本，不一致不许发
链路能看到版本generation 上要带提示词名和版本号，用了兜底副本时 Langfuse 不建关联ctx.llm 收到 prompt=p 就写 langfuse.observation.prompt.name / version；用兜底副本时打 keel.prompt.fallback=true，链路节点上标黄

边界：Dify 智能体的提示词在 Dify 应用里管，Keel 不接管。提示词不能跨智能体共用，名字强制带智能体前缀。模型仍由 manifest 决定，提示词 config 里只认 temperature、max_tokens、top_p，写了 model 会被忽略并告警。审计只记版本号、内容哈希和改动行数，不记提示词原文。

职责边界

边界划清楚，底座才不会越做越重，智能体也不会越做越乱。

Keel 底座负责

  • 身份认证、准入、配额、限流（keel-gateway，上线前由 SDK 承担）
  • 模型接入、路由、降级、计费、密钥（薄网关）
  • 智能体登记、在线探测、对账、下线
  • 知识检索（rag-forge，作为共享服务纳入监控）
  • 追踪的采集、存储、展示
  • 审计的格式、存储、防篡改、查询、导出审批
  • 发布门禁（数据集、实验、评估器用 Langfuse）
  • 线上质量汇总（打分、标注、坏案例回流用 Langfuse）
  • 工具注册、风险分级、审批流
  • 护栏策略执行
  • SDK、脚手架、CI 模板、keel-lite

智能体自己负责

  • 业务流程和推理逻辑
  • 提示词内容（在 Langfuse 里维护版本）
  • 业务工具的实现（查告警、改简历、执行 SQL）
  • 评测数据：什么算答对，只有业务方知道
  • 领域评分函数：故障类型判定、SQL 结果比对
  • agent.yaml 里的声明：模型、知识库、工具、风险等级、门禁阈值
  • 坏案例的业务判断（是缺陷还是预期内）

判断标准：一段代码如果在第二个智能体里也要写一遍，它就属于底座。

Langfuse、薄网关和 Keel 的分工

交给 Langfuse，模型调用交给薄网关

  • 模型网关（keel-llm，Keel 自研）：多厂商接入、OpenAI 兼容接口、虚拟 Key、人民币日预算、降级重试、花费记录。不向 Langfuse 上报
  • 追踪：接收和存储（OTLP、LangGraph 回调、Dify 集成），调用树、时间线、Agent Graph、多轮会话
  • 评测：数据集、实验、两版对比、大模型裁判和代码评分器
  • 质量：用户反馈、线上采样打分、人工标注队列、看板和告警、坏案例加入数据集
  • 提示词：版本管理、production / staging 标签、在线调试
  • token 和成本统计（百炼等国内模型要在 Model Definitions 里配价格）

Keel 自己做

  • 业务审计：谁通过智能体做了什么，不可篡改、不采样、导出要审批
  • 发布门禁：CI 里按维度判定退步，不达标就不许发布；提示词切到 production 也要过门禁
  • 入口网关 keel-gateway（自研）
  • 工具审批；注册中心（登记、探测、对账，并替智能体在 薄网关、Langfuse 里开通和吊销 Key）
  • 跨智能体总览：调 Langfuse 和 薄网关 的 API 按智能体拆分耗时、成本、质量指标，标出关键路径
  • 把审计、审批、门禁信息挂到链路节点上
云端套餐边界：当前账号是 Hobby，没有企业 SSO，网页用户 2 个，每月 5 万单位，保留 30 天，Metrics API 每天 100 次。邮箱密码登录即可，SDK 和 keel-server 用项目 API Key，不依赖 SSO。提示词仍只通过 keel release 切 production 标签，Keel 比对漂移并写审计；敏感字段在 SDK 上报前脱敏。生产上的 5 分钟对账和总览轮询会打满 Hobby 的 metrics 配额，升 Core 后再按分钟级查 Langfuse。薄网关没有单独的管理界面，模型、Key 和花费都在 Keel 控制台看。

方案怎么做费用参考适合
采用：Langfuse Cloud 日本主机 https://jp.cloud.langfuse.com。dev、staging、prod 三个项目在云端界面创建。智能体只配置地址和项目 Key。2026-10-04 已从云服务器 8.163.30.216 实测读写Hobby 免费。生产对账和总览升 Core，约 29 美元/月起现在：不买机器，不运维 ClickHouse

云端要注意：
① OTLP 上报必须带请求头 x-langfuse-ingestion-version: 4，只走 HTTP，不走 gRPC。漏了请求头时服务不报错，数据大约 15 分钟后才可见。
② 密钥按区域隔离。日本项目的 Key 不能拿去打美国或欧盟主机。
③ 追踪数据在 AWS 东京。审计仍在自有 PostgreSQL，两者用 keel.audit_ids 互跳。
④ 2026-09-16 及之后创建的组织，GET /api/public/traces 返回 410。读链路用 Observations API v2。
⑤ Hobby 的 Metrics API 每天 100 次。对账任务在 Hobby 上每天向 Langfuse 查一次流量，调用数以薄网关为准。
⑥ 三个环境项目手工创建。Keel 不调用项目管理 API。

关键风险与对策

风险对策
底座故障拖垮所有智能体追踪上报异步、失败本地缓冲；keel-gateway、薄网关、keel-audit 各两副本；只有高风险审计同步写入
自研网关的鉴权或流式出漏洞JWT 用 Spring Security 资源服务器验签，不自己解析；SSE 断开取消、心跳、超时先写测试用例；SDK 保留轻量校验作为双保险
薄网关 成为单点两副本加就绪探针；它是无状态的，Key 和花费在 PG 里，挂了重启即可；智能体只认 OpenAI 兼容接口，以后换成 Higress 或自研也只改地址
有人绕过底座直接调模型厂商密钥只放在 薄网关，智能体手里没有；keel-gate 扫描代码里直接调厂商 SDK 的写法；对账发现未登记的实例就告警
SDK 版本不一致契约带版本号 keel/v1，平台向后兼容两个小版本；注册自检时检查 SDK 版本
底座越做越重，新智能体绕开它只把"第二个智能体也要写"的东西纳入底座；agent.yaml 除 name、endpoint 外都有默认值
评测集质量差，门禁形同虚设模板自带冒烟用例；坏案例持续回流；门禁同时约束总分和单维度退步
过度依赖 Langfuse，以后想换智能体只通过 Keel SDK 和 OTel 协议上报，不直接调 Langfuse 专有接口；评测用例的初始版本留在 git 里；门禁逻辑在 keel-gate，不绑定 Langfuse 界面
