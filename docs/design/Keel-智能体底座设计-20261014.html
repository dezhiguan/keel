Keel 龙骨

智能体平台底座：只建一次，所有智能体复用

龙骨是船底那根纵梁。船上装什么货各不相同，但每条船都靠它承重。Keel 对智能体也是这个角色：鉴权、模型调用、知识检索、链路追踪、审计、评测、质量监控、工具审批、人工介入与恢复都由底座承担，每个智能体只写自己的业务逻辑。

02

设计原则与总体架构

这五条原则决定底座能不能真正被复用。有一条没做到，新智能体最后都会绕开底座，自己再写一套。

P1

智能体只写业务

追踪、审计、评测、鉴权、模型调用由 SDK 自动完成，业务代码里不出现上报逻辑。

P2

协议优先于代码库

Python 和 Java 共用的是 HTTP + SSE + 统一事件格式，SDK 只是协议的薄封装。换语言、换框架、换成 Dify 都能接入。

P3

上报不阻塞业务

追踪异步批量上报，失败先写本地缓冲再重试。高风险审计例外：写不进去就拒绝执行。

P4

评测是门禁，不是报表

分数低于阈值自动阻止发布。评测集随代码版本化，改提示词也要过门禁。

P5

复用已有，薄处自研

auth-gateway、rag-forge 直接成为底座组件。追踪、评测、质量用 Langfuse Cloud（日本节点）。模型网关自研一层薄代理：OpenAI 兼容、虚拟 Key、按人民币计的日预算和降级。Keel 再做这两边覆盖不了的治理，并把它们串成一个整体。

03

控制台演示

Keel 控制台的交互原型，左侧菜单可以点击切换。所有智能体（包括用 Dify 做的客服）在同一套页面里看追踪、评测、质量和审计。链路追踪页演示了一次多智能体调用：运维总控把任务并行委派给 askdb 和 offshore-wind，可以在协作图、泳道时间线、调用树三种视图间切换，点任意节点看详情。正式控制台的链路追踪先是可筛选、可分页的调用列表，点一行进入这样的详情；单智能体调用只有泳道和调用树，见控制台原型 docs/console/Keel-控制台前端-20261014.html。审计页的记录可以点开，审批卡片可以点批准或驳回。

十项共享能力

每一项都注明从你哪个项目里抽取。大部分不用从零写，而是把已经验证过的实现升级成独立服务。

C01

入口网关keel-gateway · 自研 · 先做轻量版

所有外部流量的统一入口，基于 Spring Cloud Gateway。

  • 按注册中心动态路由，只放行"上线"状态的智能体
  • 用 auth-gateway 的 JWKS 验签（用户 token 的 aud 统一为 keel-api），按角色准入
  • 按用户、组织、智能体做配额和并发控制（Redis）
  • Token Exchange 换成目标智能体 aud 的 token 再转发
  • SSE 透传，客户端断开时取消上游；生成根 span，写调用级审计
  • 上线前这些由 SDK 在智能体入口完成，上线后 SDK 只保留轻量校验
来源：auth-gateway（复用）+ askdb quota.py
C02

模型网关自研薄网关 keel-llm

自研一层 OpenAI 兼容代理，智能体只认模型别名。

  • 厂商密钥只放在薄网关；注册时给智能体创建虚拟 Key，限定可用模型和人民币日预算
  • 超时降级按该 Key 的 fallback 列表，由 agent.yaml 生成。向量化不允许降级
  • 成本按虚拟 Key 统计到智能体，单位是人民币；按步骤的成本在 Langfuse 的 generation 上看
  • 智能体只能通过 ctx.llm 调模型，keel-gate 检查代码里直接调厂商 SDK 的写法
来源：自研薄网关 + careermate Provider 抽象

  • 检索结果自带 citations，供接地校验和评测使用
  • 检索作为 retriever 节点进调用方的 trace，分段耗时写成子 span

  • 多智能体：子智能体是 agent 类型节点，跨服务靠 traceparent 串进同一个 trace，自动生成 Agent Graph

C10

审批中心与人工介入approval · run lifecycle

所有需要人点一下的事集中到一处，智能体不用各自建后台。

  • 四类审批共用一张表（subject_type）：工具调用、工具变更（风险调低也要批）、智能体配置与下线、数据导出。不是只有工具调用要审批
  • 人工介入是另一回事：执行挂起等人回话（input_required）或转人工（handoff），没有审批单，处理完从断点继续
  • 挂起时 SSE 流正常关闭，网关借此释放并发位；恢复时重新换票（原票 600 秒必然已过期）
  • 边界：底座管账，智能体管现场。底座存 run 状态、谁有权决定、截止时间、恢复入口；现场只存一个 checkpoint_ref，内容不碰。底座永远不决定下一步做什么——那是工作流引擎，不是 Keel
  • v1 不提供现场存储实现，askdb 继续用自带的 LangGraph checkpointer
来源：askdb approvals.py + LangGraph checkpoint；详见 docs/specs/p0/P0-1a-run-lifecycle.md

薄网关 和 Langfuse 怎么融进底座

不是在控制台放两个跳转按钮。集成分三层：开发者日常看的、日常做的操作都在 Keel 里完成，只有深入排查时才带着上下文跳过去。

层做什么具体做法
① 运行时打通
开发者看不见		智能体不直接感知 薄网关 和 Langfuse，由 SDK 在背后接好ctx.llm 的地址指向 薄网关，带上该智能体的虚拟 Key，以及 agent、trace_id、session_id 等 metadata；每次模型调用由 SDK 记成 Langfuse 的 generation，挂在当前 trace 下。薄网关 自带的 Langfuse 回调关闭，避免重复记录
② 控制台取数
高频看的放在 Keel		Keel 后端调两边的 API，汇总成跨智能体视图总览、质量、评测页调 Langfuse 的 traces、scores、datasets 接口；模型网关页调 薄网关 的花费日志、Key 信息、模型列表接口。深挖时用深链跳转：追踪节点带 trace_id 跳到那条 Langfuse 链路，评测页跳到对应实验。不用 iframe 整页嵌入，跨域登录和权限都会出问题
③ 配置自动化
写操作由 Keel 代办		开发者不用去两边手工配置keel register 时：在 薄网关 创建虚拟 Key（限定模型、日预算）；把两边的 Key 写进该智能体的 K8s Secret；在 Langfuse 导入评测数据集。keel release 时把门禁实测的那一版提示词打上 production 标签；控制台改提示词由 keel-server 代写 Langfuse。keel retire 时吊销虚拟 Key。每一步都写审计
登录尽量一次登录auth-gateway 目前不是 OIDC 提供方（没有授权端点和发现端点），Langfuse 暂时接不了它的单点登录：先用邮箱密码并关闭自助注册，账号由管理员创建；auth-gateway 以后补上 OIDC 再接。薄网关没有单独的管理界面，模型、Key 和预算都在 Keel 控制台里看
控制台登录底座自己的登录态，不和业务项目共用只登录不注册，账号密码或短信验证码，经 auth-gateway 认证。控制台 token 的受众是单独的 keel-console：careermate 等项目的 token 进不了控制台，控制台的 token 也调不了智能体、进不了别的项目。默认只有一个控制台用户（官德志，平台管理员）。另有预览模式：不登录能看全部页面，所有写操作前端置灰、后端拒绝，且看不到用户原文

底座怎么知道智能体上线、下线了

以注册中心为准，再用运行时信号核对：主动登记决定"应该有哪些"，运行时探测确认"实际在跑哪些"，定期对账找出两边的差异。

登记与探测

  • 主动登记：keel register → 已注册；keel release 过门禁 → 上线；keel retire → 已下线。Key 只在注册时发放，没登记的智能体调不了模型、报不了追踪
  • K8s 探测（k3s 上的智能体）：Deployment 打标签 keel.io/agent，注册中心 watch 这些 Pod，就绪探针用 /v1/health；再调 /v1/manifest 核对运行版本和登记版本
  • SDK 心跳（函数计算、定时任务、集群外服务）：启动时上报实例，每 15 秒续约，45 秒无心跳记为离线
  • API 探活（Dify 应用）：注册中心定时调一次 Dify API

每 5 分钟对账

  • 登记了、在运行、有流量 → 正常
  • 登记了、不在运行 → 离线，告警并通知负责人，保留 Key 和配置
  • 在运行、很久没有流量 → 僵尸，提示是否下线
  • 在运行、没登记 → 未登记，告警（有人绕过了流程）
  • 已下线、仍在运行 → 下线不彻底，告警并确认 Key 已吊销
  • 流量从 Langfuse（按 agent 数 trace）和 薄网关（按虚拟 Key 数调用）两边取
要不要用 Nacos：Java 智能体多、服务发现本来就用 Nacos 时，可以让 Nacos 承担"在不在线"这一层；manifest、状态机、Key 发放这些治理数据仍放在 Keel 注册中心。现在的规模直接用 K8s watch 就够了，不必多引入一个组件。

自研 keel-gateway：先做轻量版

选自研不选 Higress：模型代理已经交给 薄网关，入口网关的核心（按注册中心路由、Keel 审计契约、渠道协议适配）本质是业务逻辑，用 Java 写比写 Wasm 插件好开发、好调试，资源占用也小。基于 Spring Cloud Gateway，JWT 验签、Redis 限流、SSE 都有现成支持。

模块轻量版（P2，约 2～3 周）完整版（P3 起按需）
路由/agents/{name}/v1/invoke 按注册中心的 endpoint 转发；路由表本地缓存，变更推送，不重启；只放行"上线"状态按用户或比例灰度到新版本
鉴权准入JWKS 验签（Spring Security 资源服务器，不自己解析 token），要求 aud=keel-api，按 manifest 里的角色准入；Token Exchange 换成目标智能体 aud 的 token（用户 token 只有一个 aud，必须换票）开放 API 的 API Key；企业微信、钉钉回调验签
配额用户、组织、智能体三个维度的 Redis 令牌桶；并发会话数上限（SSE 是长连接，只限 QPS 不够）日调用上限、按组织的套餐
流式SSE 透传：关缓冲、长超时、心跳；客户端断开时取消上游请求输出流式 PII 脱敏（滑动缓冲，跨 token 块识别）
护栏长度限制；其余仍在 SDK输入注入检测、敏感词前移到网关
追踪审计生成根 traceparent 并上报根 span；每次调用（含被拦截的）写一条 invoke 审计事件，经 RocketMQ 异步入库按智能体的首 token 时间、拦截次数看板
协议适配—企业微信、钉钉、Dify 转成标准 /v1/invoke
韧性每个智能体单独超时；两副本熔断，智能体挂了返回友好提示或转人工；只对非流式幂等请求重试
和 SDK 的分工：网关上线后，JWT 准入、用户配额、调用级审计移到网关；SDK 保留轻量 JWT 校验作为双保险，工具审计、审批、接地校验、ctx.llm 都不变。配一条 K8s NetworkPolicy，智能体只接受来自网关的流量，防止绕过网关直接调智能体。TLS 证书、WAF 这类通用流量管理交给前面的 Nginx 或阿里云 SLB，网关只做智能体特有的事。

rag-forge 被多个智能体共用，按"共享服务"接入：登记、追踪、看板、成本、审计都进底座，但不当成智能体，不走评测门禁。它已有的分段耗时、检索评测、成本中心都能直接复用。

为什么统一调用协议

@scorer("fault_type_match")
def fault_type_match(case, output) -> Score:
    got = output.meta.get("fault_type")
    ok = got == case.expected["fault_type"]
    return Score(value=1.0 if ok else 0.0, reason=f"判定为 {got}")

提示词怎么管

底座要管提示词，原因有三条：改提示词和改代码一样会让效果退步，必须过门禁；业务方要能自己改，不能每次找开发发版；出了问题要能从一条链路查到当时用的是哪一版。存储、版本、diff、调试台直接用 Langfuse，Keel 补上它在我们这套部署下缺的几件事。

  • 智能体登记、在线探测、对账、下线
  • 知识检索（rag-forge，作为共享服务纳入监控）
  • 追踪的采集、存储、展示
  • 审计的格式、存储、防篡改、查询、导出审批
  • 发布门禁（数据集、实验、评估器用 Langfuse）
  • 线上质量汇总（打分、标注、坏案例回流用 Langfuse）
  • 工具注册、风险分级、审批流
  • 护栏策略执行
  • SDK、脚手架、CI 模板、keel-lite

智能体自己负责

  • 业务流程和推理逻辑
  • 提示词内容（在 Langfuse 里维护版本）
  • 业务工具的实现（查告警、改简历、执行 SQL）
  • 评测数据：什么算答对，只有业务方知道
  • 领域评分函数：故障类型判定、SQL 结果比对

  • 坏案例的业务判断（是缺陷还是预期内）

人工介入开发

智能体生产的数字员工不是黑盒。每名员工都有独立的 Git 仓库，人和研发员工在同一个 PR 上协作；流水线只负责把员工送到 staging，上生产由人决定。

AUTO

全托管

研发员工写全部代码，人只在四个关口出手。

  • 人可以随时往 PR 推提交，dev-agent 以人的提交为准
  • 出问题可以一键接管
适合：只读、低风险、需求清楚的员工，如发布说明、周报
COLLAB

人机协作

研发员工写代码，每一轮 PR 必须有一名人工 reviewer 通过才进门禁。人写的代码，智能体不能覆盖。

  • 分支保护要求至少 1 个人工 approve
  • 和人的改动冲突时 dev-agent 挂起问人
适合：有写操作或 mid 风险工具的员工；元智能体生产研发员工时强制使用
SCAFFOLD

只生成骨架

研发员工只出需求单、岗位说明书、评测集和项目骨架 PR，然后任务进入人工开发；人写完点"提交门禁"，后面的评审、门禁、发布照常走。

适合：业务逻辑复杂、需要对接内部系统、含 high 风险工具的员工

为什么说"不直接部署"

  • 流水线的产出是三样东西：keel-agents/{name} 仓库、一个 PR、一个 staging 预览环境。staging 只对内开放，经网关路由只对测试身份可见。
  • 上生产只有一条路：H4 批准 → 合并 PR → 仓库 CI 跑 keel gate --env prod 和 keel release。研发员工没有任何直接调发布接口的工具。
  • keel-server 对由智能体生产的员工多一条校验：发布记录必须关联一张已批准的 git.pr.merge 审批单，否则 keel release 被拒。
  • 协作模式和研发层任务再加一道 Git 分支保护：没有人工 approve 的 PR 合不进去，即使审批单批了也一样。

守住三条线

智能体生产智能体，最大的风险不是代码写得不好，而是自己出题自己考、自己给自己开权限、自己改自己。这三条线在机制上堵死，不靠提示词约束。

考题由人出

  • 种子用例由业务负责人上传，打 origin:human，每个任务至少 30 条（起步值）
  • H2 确认时 keel-server 随机切出 30% 作为隐藏考题，存 keel 库 devflow_holdout，不进 Langfuse 数据集
  • 研发员工没有读隐藏考题的工具；沙箱不放行 Langfuse 和 keel-server
  • 隐藏考题只在 CI 里用 CI 身份拉取、本地跑，只回写按 tag 的聚合分
  • 研发员工自己的考题也由人出，eval-agent 不能给研发员工出题

权限由人批

  • 共享工具和知识库只能经所有者审批写入 agent_tool_grant，没有任何数字员工能写
  • spec-agent 只能选注册表里的工具，风险不能低于登记值；注册自检再校验一次
  • 含 risk: high 工具的员工，审批策略由平台管理员绑定
  • production 提示词标签只经 keel release
  • 流水线新建 Key 的日预算上限 ¥50（可配），超出要平台管理员审批

不能改自己和上级

  • 生产方向只能向下：人 → 元智能体 → 研发员工 → 业务员工
  • meta-agent 只能由人修改；它的仓库不在 keel-agents/ 组织下，研发员工没有写权限
  • 研发员工的升级只能由 meta-agent 发起任务，研发流水线拒绝接研发层任务
  • 任何员工都不能接"修改自己"的任务；keel-server 按 devflow_job.target_agent 与执行者比对后拒绝
  • 研发员工改提示词同样要经 staging 回归和 keel release

SDK 与运行时

智能体的三项核心要素做成底座能力，治理统一在 SDK 里实现，跑在智能体自己的进程内。服务端不做编排引擎。

能力设计
工具调用ctx.llm.chat 增加可选参数 tools，返回内容 + tool_calls；现有调用方不变。薄网关原样转发，能力表标出哪些模型支持。
ctx.loopSDK 里的函数，不是底座远程控制。停止条件统一：目标完成、步数上限（执行 budget.maxSteps）、预算上限（委派时向下传）、原地打转（同工具同参数连续 2 次）。循环内高风险工具存 checkpoint 后发 suspend，恢复后接着跑。每步一个 span，属性 keel.loop.step。
执行方式三档从最简单的选起：① 普通代码，固定流程用；② ctx.loop；③ 图，只在有回退、并行、中途等人时用，Python 适配 LangGraph（挂起恢复、追踪、预算）；Java 暂不做图。
ctx.memory运行内上下文由 loop 自动累积；会话记忆、用户记忆存独立库 keel_memory（PG + pgvector）；评测流量（eval_run_id 非空）一律不写；用户可查可删，审计只记条数和类别。
ctx.skills技能 = 说明 + 依赖工具 + 示例 + 用例，manifest spec.skills 锁定版本，按需加载进上下文。技能不带权限，依赖的工具和知识库分别走 H3；风险继承依赖工具中最高的。
独立运行模式KEEL_MODE=standalone：模型直连任意 OpenAI 兼容地址，提示词读本地 prompts/，审计写本地（keel-lite），追踪可选，不需要注册。默认受治理模式，生产必须受治理。
层级会话记忆用户记忆任务记忆经验记忆

模型网关：一次请求的生命周期

吸收 2026-10-13 网关功能设计稿：按"接入 → 准入 → 决策与执行 → 结算"组织。可观测不单独成层，分到账单、链路追踪和平台告警三处，避免和链路追踪重复。

阶段设计
接入 · 模型与渠道能力表（对话、工具调用、JSON、流式、向量维度、上下文）；价格带版本（人民币 / 百万 token，含缓存命中），缺单价拒绝启动；接入流程 草稿 → 检查 → 小额真实调用 → 灰度 → 启用；健康分 已配置 / 已探测 / 有真实调用；配置漂移检查；向量模型固定不降级，不做 /rerank。
准入 · Key 与配额Key 带版本、可轮换、旧版本永久失效，明文只显示一次；每个 Key 独立校验可用模型、日预算、RPM / TPM、并发；额度原子预留，跨副本一致；预算四层：组织 → 智能体 × 环境 → 单次运行（x-keel-run-budget）→ 研发任务。
决策与执行 · 路由与降级显式指定直接用；否则硬约束过滤（授权、上下文、工具能力、健康）后按 均衡 / 成本优先 / 延迟优先 排序；只对超时、5xx、遵守 Retry-After 的 429 降级，最多切换 1 次；鉴权失败、预算不足不换模型；流式开始输出后不重放；按渠道熔断（关闭 → 打开 → 半开）；策略带版本，回放 → 灰度 → 发布，可回滚；提供路由试算。
结算 · 账单按实际 usage 结算、退回预留，同一 requestId 只结算一次；usage 缺失进入待计费；账单落 PG keel_llm，每条带 requestId、attemptId、traceId、价格版本、路由版本；识别重试、降级、截断等浪费。
可观测（分散）链路追踪的 generation 节点按 requestId 读账单，显示每次尝试、实际模型、路由原因和费用；Langfuse 仍只由 SDK 上报一次。告警规则在网关页配置，告警进入总览"告警与事件"。网关服务指标进 Prometheus / SkyWalking。
分期内容验收
P0旧 Key 永久失效；额度预留 + 结算 + 退款；幂等结算与崩溃补偿旧 Key 始终 401；并发额度守恒
P1账单落 PG（稳定游标分页）；待计费；真实流式及取消 / 中断结算；RPM / TPM / 并发；接入向量模型完整对账、流式可用、向量兼容
P2路由策略与试算；熔断；灰度回滚；链路显示网关尝试；告警规则决策可解释、故障可恢复、费用可归因
先补接口约束：新增的网关管理接口（策略、部署与熔断状态、账单按日汇总等）先写进技术文档和 .cursor/rules/external-apis.mdc，再实现。
