全流程智能体化

元智能体生产研发员工，研发员工批量生产业务员工；人随时能接手开发，上生产必须人批

Keel 底座已经承担了鉴权、模型、追踪、审计、评测和发布门禁。本方案在底座之上把研发流程本身交给智能体，并把每个智能体当成一名数字员工：有岗位说明书（agent.yaml）、入职考核（评测与门禁）、试用期（staging）、权限、预算和人类直属负责人。研发流程由智能体执行，但产出的是代码仓库、PR 和 staging 预览环境，不直接部署生产。

手写 1 个元智能体元智能体生产 7 名研发员工研发流水线批量生产业务员工三种开发模式 · 随时人工接管不改 keel/v1 契约枚举
1个需要人手写的智能体：元智能体，其余都由智能体生产
3层元智能体 → 研发数字员工 → 业务数字员工，只能向下生产
4个人工关口：需求确认、评测确认、授权审批、发布审批
0次智能体直接部署生产的机会，生产发布只经人批 + CI

02

新增哪些数字员工

手写 1 个元智能体，由它生产 7 名研发数字员工。全部是普通 Keel 智能体：有自己的 manifest、虚拟 Key、预算、评测集和门禁，和业务员工走同一套注册与发布流程，没有任何特权。

元智能体 · 手写
meta-agent

元智能体带新人的架构师

生产和升级研发数字员工。研发员工还不存在时它要能独自走完全流程，所以它是一个自带"需求 → 评测草稿 → 开发 → 门禁"步骤的单体智能体，比研发流水线慢，但每一步都有人看着。

  • 模板 graph-agent，Python，人工编写、只由人修改
  • 只接"研发层"任务，不生产业务员工
  • 它的任务强制人机协作模式：每个 PR 必须有人工 review 通过
  • 四个关口的审批人都是平台管理员
工具：devflow.job.read · devflow.stage.report · sandbox.run · git.repo.create · git.branch.push · git.pr.open · ci.workflow.dispatch · git.pr.merge（high）
日预算：¥50（估算）
研发 · 元智能体生产
dev-lead

研发组长流水线总控

接收业务员工的生产任务（单个或批量），按阶段委派给其他研发员工，管预算、修复轮次、人工关口和人工接管。自己不写代码、不改配置。

  • 模板 supervisor
  • delegates：spec-agent、eval-agent、dev-agent、code-review、ci-doctor、release-agent
  • 批量任务按并发上限排队
工具：devflow.job.read · devflow.stage.report · devflow.batch.read
日预算：¥30
研发 · 元智能体生产
spec-agent

需求分析师

把需求表单变成需求单：目标用户、输入输出、成功标准、模板、工具与知识库、风险等级、预算建议，并起草岗位说明书 agent.yaml。批量需求时还会找出彼此重复的需求。

  • 模板 graph-agent；输入护栏 inputInjection: enforce
  • 只能从工具注册表选工具，风险等级不得低于登记值
工具：devflow.catalog.search · devflow.stage.report
产物：需求单 · manifest 草稿 · 授权清单
研发 · 元智能体生产
dev-agent

开发工程师

按 keel new 模板生成项目，写业务代码、工具、提示词兜底副本和单测，在沙箱里跑 pytest 和协议自检，通过后推分支、开 PR。协作模式下以人的提交为准，不覆盖人写的代码。

  • 模板 graph-agent；F4 起支持 java-spring
  • 代码只在沙箱执行；看不到隐藏考题
  • 和人的改动冲突时挂起问人（input_required）
工具：sandbox.run · git.repo.create · git.branch.push · git.pr.open
需要编码模型，见第 11 节
研发 · 元智能体生产
eval-agent

测试工程师

在人给的种子用例上扩充边界、对抗、注入类用例，按 tags 补齐覆盖，起草领域评分函数 @scorer。扩充用例经人审过才计入门禁。

  • 模板 tool-agent
  • 不能修改或删除人给的用例；拿不到隐藏考题
工具：devflow.job.read · sandbox.run · devflow.stage.report
研发 · 元智能体生产
code-review

代码评审员原计划 P3 手写

评审流水线上的每个 PR，包括人写的提交。重点查：是否绕过 ctx.llm、审计字段是否超白名单、高风险工具是否声明审批、是否针对可见用例特判。

工具：git.pr.diff · git.pr.comment · 知识库 dev-standards
研发 · 元智能体生产
ci-doctor

CI 诊断员原计划 P3 手写

CI 或门禁失败时读日志和门禁报告，按维度定位退步原因，给 dev-agent 或接手的人一份修复清单。

工具：ci.log.fetch · keel.gate.report.read
研发 · 元智能体生产
release-agent

发布工程师

部署 PR 分支到 staging、跑门禁和隐藏考题，读报告。通过后申请合并 PR；合并是高风险工具，自动挂起等发布审批，批准后由 CI 跑 keel release。上线后观察 7 天。

  • 模板 tool-agent；不直接调 keel release
  • 质量退化只能提回滚审批单，不能自己回滚
工具：ci.workflow.dispatch · keel.gate.report.read · git.pr.merge（risk: high）

03

两条生产线

两条线走同一套阶段和关口，区别在谁来干活、谁来批。研发层任务只能由元智能体接，业务层任务只能由研发流水线接。

元智能体生产线研发流水线
产出研发数字员工（新建或升级）业务数字员工（新建或改造）
谁干活meta-agent 一个人走完全部步骤dev-lead 编排 6 名研发员工分工
开发模式强制人机协作，每个 PR 都要人工 review按任务选：全托管 / 人机协作 / 只生成骨架
关口审批人H1～H4 全部是平台管理员H1 需求人、H2 业务负责人、H3 所有者、H4 负责人
批量不支持，一次一个支持批次，按并发上限排队
量级一共 7 名研发员工，偶尔升级按业务需求持续生产

批量生产业务员工

  • 业务方在控制台上传一张需求表（每行一名员工：名称、目标、场景、输入输出、成功标准、负责人），生成一个批次，每行是一个独立任务。
  • spec-agent 先整批过一遍：标出彼此重复或能合并的需求、标出缺信息的行，再逐条出需求单。
  • H1、H2 支持在批次视图里逐条确认，一屏看完；但每个任务仍单独记审计、单独挂起和恢复。

04

人工介入开发

智能体生产的数字员工不是黑盒。每名员工都有独立的 Git 仓库，人和研发员工在同一个 PR 上协作；流水线只负责把员工送到 staging，上生产由人决定。

AUTO

全托管

研发员工写全部代码，人只在四个关口出手。

  • 人可以随时往 PR 推提交，dev-agent 以人的提交为准
  • 出问题可以一键接管
适合：只读、低风险、需求清楚的员工，如发布说明、周报
COLLAB

人机协作

研发员工写代码，每一轮 PR 必须有一名人工 reviewer 通过才进门禁。人写的代码，智能体不能覆盖。

  • 分支保护要求至少 1 个人工 approve
  • 和人的改动冲突时 dev-agent 挂起问人
适合：有写操作或 mid 风险工具的员工；元智能体生产研发员工时强制使用
SCAFFOLD

只生成骨架

研发员工只出需求单、岗位说明书、评测集和项目骨架 PR，然后任务进入人工开发；人写完点"提交门禁"，后面的评审、门禁、发布照常走。

适合：业务逻辑复杂、需要对接内部系统、含 high 风险工具的员工

随时接管与交还

动作什么时候能做发生什么
人工接管开发、评审、门禁、诊断阶段，或任务失败后任务进入 HUMAN_DEV；dev-agent 停止推送；修复轮次暂停计数；接管人成为该任务的当前开发者，记 config.change 审计
请智能体帮忙人工开发中在任务里给 dev-agent 发一条具体指令（例如"补齐 tools/ 的单测"），它只在指定范围内改，改完回到人工开发
交还智能体人工开发中回到 REVIEW：code-review 评审包括人写部分在内的全部改动，然后进门禁；dev-agent 后续修复以人的提交为基线
提交门禁骨架模式人工开发完成同"交还"，但后续修复默认仍由人来做
放弃任意阶段任务 CANCELLED，staging 资源逆序回收，仓库保留只读

为什么说"不直接部署"

  • 流水线的产出是三样东西：keel-agents/{name} 仓库、一个 PR、一个 staging 预览环境。staging 只对内开放，经网关路由只对测试身份可见。
  • 上生产只有一条路：H4 批准 → 合并 PR → 仓库 CI 跑 keel gate --env prod 和 keel release。研发员工没有任何直接调发布接口的工具。
  • keel-server 对由智能体生产的员工多一条校验：发布记录必须关联一张已批准的 git.pr.merge 审批单，否则 keel release 被拒。
  • 协作模式和研发层任务再加一道 Git 分支保护：没有人工 approve 的 PR 合不进去，即使审批单批了也一样。
05

守住三条线

智能体生产智能体，最大的风险不是代码写得不好，而是自己出题自己考、自己给自己开权限、自己改自己。这三条线在机制上堵死，不靠提示词约束。

考题由人出

  • 种子用例由业务负责人上传，打 origin:human，每个任务至少 30 条（起步值）
  • H2 确认时 keel-server 随机切出 30% 作为隐藏考题，存 keel 库 devflow_holdout，不进 Langfuse 数据集
  • 研发员工没有读隐藏考题的工具；沙箱不放行 Langfuse 和 keel-server
  • 隐藏考题只在 CI 里用 CI 身份拉取、本地跑，只回写按 tag 的聚合分
  • 研发员工自己的考题也由人出，eval-agent 不能给研发员工出题

权限由人批

  • 共享工具和知识库只能经所有者审批写入 agent_tool_grant，没有任何数字员工能写
  • spec-agent 只能选注册表里的工具，风险不能低于登记值；注册自检再校验一次
  • 含 risk: high 工具的员工，审批策略由平台管理员绑定
  • production 提示词标签只经 keel release
  • 流水线新建 Key 的日预算上限 ¥50（可配），超出要平台管理员审批

不能改自己和上级

  • 生产方向只能向下：人 → 元智能体 → 研发员工 → 业务员工
  • meta-agent 只能由人修改；它的仓库不在 keel-agents/ 组织下，研发员工没有写权限
  • 研发员工的升级只能由 meta-agent 发起任务，研发流水线拒绝接研发层任务
  • 任何员工都不能接"修改自己"的任务；keel-server 按 devflow_job.target_agent 与执行者比对后拒绝
  • 研发员工改提示词同样要经 staging 回归和 keel release

指标、成本与风险

这套流程好不好用看下面五个数。目标值是业务批量生产开始时的起步线，试点后再定正式值。

≤ 1 工作日需求提交 → staging 门禁通过（全托管，不含人工等待）
≥ 50%首次门禁通过率；3 轮内 ≥ 85%
≤ 30%需要人工接管的任务占比
0 条生成代码违规：厂商 SDK、硬编码 Key、超白名单审计字段
待实测每个任务的模型花费，默认预算上限 ¥80
