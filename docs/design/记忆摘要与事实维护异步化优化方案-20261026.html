01 / OBSERVED BASELINE

本次要解决的等待

样本：Trace 7207a7d8437de0416d7aef02e5342788。整条请求 12.763 秒，主回答模型直到第 7.130 秒才开始。facts 与摘要都在主回答启动前同步执行。

facts 1.778s摘要 3.896s主回答 5.622s其他 1.467s
环节观测耗时问题
memory.facts1.778 秒；包含 0.972 秒、0.665 秒两次模型调用与摘要串行，且本次状态为 conflict / fallback。
memory.summary3.896 秒生成摘要阻塞主回答；0ms 的另一 summary 节点只是读取/状态观测。
合计5.674 秒，占请求约 44.5%只优化摘要仍会留下约 1.78 秒 facts 等待。

父 span 与其内部 llm.chat 是包含关系，不重复相加。5.674 秒是本样本拟后移的串行工作量，不是已验证的首字提速承诺；主模型耗时也包含输出生成时间。

范围只限本次优化：调整摘要与 facts 的读写时机、后台任务可靠性和验收。沿用现有历史检索、权限边界、上下文硬上限和原文存储，不扩展其他业务模块，也不承诺新增永久记忆。
02 / TARGET FLOW

回答优先，记忆随后更新

回答前 · 轻量读取

  1. 读取已有摘要、已有事实账本及各自的版本/处理进度。
  2. 保留当前问题、近期完整轮次、当前相关原文和关键决定。
  3. 超过输入预算约 85% 的目标线时，按完整轮次裁剪；系统规则和当前问题不能被历史裁剪。
  4. 以已组装上下文进入主 llm.chat。常规路径不调用 purpose=memory。

回答后 · 有界维护

  1. 用户输入与最终答案持久化成功，可靠登记记忆维护任务。
  2. 后台 worker 读取一个有界、连续、完整的待处理历史前缀。
  3. 执行摘要、事实抽取及输出验证；通过版本校验后提交。
  4. 成功推进对应游标；失败保留原状态，按策略重试或报警。
当前：读历史 → 抽 facts → 写摘要 → 主回答 → 持久化
目标：读已有记忆 → 组装/裁剪 → 主回答 → 持久化
                                            └→ 可靠任务 → 更新 facts / 摘要

summary：把失败兜底升级为常规快路径

本轮优先使用已有摘要与能放下的近期完整轮次，不等待新摘要。被裁剪的未摘要消息仍保留在原文存储，标记当前上下文存在裁剪区间，需要时按现有授权回查。重要上下文无法安全保留时允许小范围同步兜底，不把“永不同步压缩”设为绝对规则。

facts：先读账本，抽取后移

常规路径只加载已有账本。后台按进度处理新增用户事实、纠正与撤回。最新用户原话必须保留并优先于旧账本；明确纠正立即作用于当前回答，冲突不明确则澄清。不能因为后台尚未更新，就把旧事实描述成已确认的最新事实。

摘要与 facts 合并调用作为第二阶段实验：只有结构化输出验证、费用和事实准确性均通过对照后才启用；即使共用一次模型调用，也分别验证、记录各自的成功进度，不能用摘要成功掩盖事实抽取失败。

03 / CORRECTNESS BOUNDARIES

让异步更新可恢复、可并发

约束本次落地要求
可靠投递不能只依赖进程内 create_task。优先在答案持久化事务内写任务/outbox，再异步分发；若现有存储不能同事务，必须补偿扫描，覆盖“答案保存成功但任务未入队”的窗口。客户端断开不等于后台任务成功。
隔离与任务范围任务绑定 agent / env / owner / session，包含目标消息上界、任务类型及预期版本。worker 重新确认会话存在、保留期和可处理范围；不沿用可能过期的用户短期票据绕过权限。
版本与游标任务中的 expected version 只用于乐观并发校验。成功才 CAS 更新内容与对应 throughId；冲突后重新读取权威状态、重新计算未处理区间，不强行覆盖或倒退游标。facts 与 summary 的进度分别管理。
去重与幂等相同会话、类型和目标区间的重复投递可合并。CAS 避免重复提交，但不能单独避免重复付费调用；需配合会话级任务合并、领取租约或等价互斥机制。
分批与重试每次最多处理四个 chunk，且每段输入也必须满足 token 上限；超过容量时选择能完成的连续前缀，而非把全部积压反复判失败。整批验证成功后只推进到实际完成的前缀末尾。限制超时、重试次数和费用；失败不推进本批游标。
过期与删除会话被删除或消息过期后，排队任务应失效；执行中也需在提交时再次校验，不能重新创建已删除的摘要或事实。
上下文完整性保留完整 user/assistant/tool 协议组；不留下孤立 tool 消息。旧摘要覆盖区间与近期原文之间有缺口时明确记录，关键事实不能被静默裁掉。保留原有输入硬上限，不为快路径放宽。
可观测性继续使用 memory.summary / memory.facts，标记 attempted / ok / failed；另记录冲突、跳过、超时、重试、处理区间及版本。后台使用独立 trace 并关联触发请求，不把原 trace 拉长到队列完成；普通日志/span 不写用户原文。
04 / IMPLEMENTATION ORDER

分两步实施，先验证最直接的收益

  1. 基线与契约：固化触发摘要/facts 的长会话样本，记录实际模型、提示词、输入预算、输出长度与版本。明确任务数据、各自进度及 CAS 行为；若变更跨语言字段，先更新契约。
  2. 第一阶段：常规路径只读记忆并裁剪；可靠投递后台任务；摘要与 facts 可分别更新。先把串行调用后移，不同时重写检索和记忆内容算法。
  3. 灰度与对照：先在个人助理 staging 开启；通过下方性能、正确性和故障用例。保留切回现有同步策略的开关；回滚不删除已提交的有效记忆。
  4. 第二阶段：实验合并摘要和 facts 的单次 purpose=memory 调用。若质量或费用未达标，保留分开维护。
05 / ACCEPTANCE PLAN

同时验收速度、记忆质量与后台可靠性

所有数值均为待验证的验收目标，不是已完成结果。对照组与候选组使用隔离但等价的会话，保持同一真实模型路由、提示词、输入预算、问句和输出长度要求；均通过正式授权入口执行，不用固定回答或假模型证明性能。

验收项执行方法通过标准
热路径调用覆盖无摘要、旧摘要、85% 阈值上下、facts 有新增四类输入；检查主回答启动前的完整调用链。常规路径主回答前 purpose=memory 模型调用为 0。明确触发同步兜底的样本单独统计。
首字与总耗时长会话对照组/候选组各至少 30 次，交替执行；统计首个非空 token、主模型启动、最终答案持久化时间。触发记忆维护的样本，候选首字 P95 比对照降低至少 30%；普通短会话首字及完成 P95 不恶化超过 10%。输出完整性与约定长度同时核对。
持续负载在同一资源配置下，以 2 QPS、4 QPS 分别持续 5 分钟，覆盖会触发维护的长会话；监测回答与后台任务。无因本次变更造成的 HTTP/SSE 错误、OOM 或重启；完成吞吐跟上到达率，在途数不持续增长。模型限额或故障导致未完成时不能记通过。
记忆收敛记录队列等待、执行、CAS 提交和 backlog；停止流量后继续观察。4 QPS 场景下目标为 95% 任务在 60 秒内完成对应进度更新，测试积压在停止流量后 5 分钟内清空；无过期/删除任务被重新写入。未达标则调整 worker、合并策略或阈值后重测。
正确性与隔离按下方用例，分别在后台未完成、完成后、跨副本时检查答案与持久化状态。关键事实、纠正、撤回、隔离和删除用例全部通过；无错误确认、丢事实或跨用户泄露。任何关键失败均阻断推广，不能被性能均值抵消。
额外成本对相同历史范围统计摘要/facts 模型调用数、token、重试和已结算费用。常态每轮维护平均成本不高于对照；冲突与重试费用单列，达到任务费用上限后停止并报警。合并调用必须单独通过质量对照。

验收记录至少包含：代码/SDK/镜像版本、配置、用例 ID、输入范围、trace 与后台 task ID、前后版本/游标、答案核对、首字/完成耗时、token/费用、资源与清理结果。凭据不写入报告。测试只清理本次创建的数据。

06 / TEST CASES

可执行验收用例

统一使用独立测试会话。示例事实为虚构测试材料：青岚项目代号 LOTUS-9813，检查日期 11 月 26 日。并发、进程退出及模型故障应在隔离的 staging 验收范围内注入并标明，不能冒充自然故障。

编号准备与操作预期结果与必查证据
M01
短会话		新会话，一次普通问答；历史低于目标线。无不必要的摘要模型调用；回答与基线一致，后台不产生空范围任务。
M02
超阈值		构造超过 budget×85% 的多轮历史，已有摘要；追问近期事实。先读旧摘要并裁剪完整轮次，主回答前无 memory 模型调用，输入不超过原硬上限；答案正确，后台随后推进进度。
M03
无旧摘要		历史已超阈值但摘要为空，问题依赖近期轮次。使用可容纳的近期完整轮次正常回答；无虚构摘要，后台按连续前缀开始维护。
M04
旧事实回查		早期写入示例代号/日期，追加填充对话使该轮离开近期窗口；在旧摘要尚未覆盖时提问。通过相关原文回查或明确兜底取得事实；不能凭空猜测，也不能把“本轮裁掉”说成“用户从未提供”。核对原文引用。
M05
当前纠正		旧账本预算 20 万；阻塞后台，本轮说“更正为 30 万”，立即问预算并连续追问。当前回答与下一轮均采用明确纠正的 30 万，保留原话；后台提交后账本收敛，不复活旧值。
M06
撤回与冲突		先明确撤回旧日期；另建案例输入两个未明确取舍的日期。撤回后不把旧日期当有效事实；未明确取舍的冲突需要澄清，不能按最新时间自行确认。
M07
连续快问		后台延迟期间，在同会话快速追加 10 轮，包含两次事实更正。回答可用新增原文；合并任务的目标上界不丢最后更正，游标单调推进，积压最终收敛。
M08
多副本 CAS		两 worker 从相同版本读取，重叠处理同一会话区间并竞争提交。只接受合法 CAS；失败者重新读取，不覆盖获胜结果、不倒退游标；重复模型付费受到领取/合并机制约束。
M09
崩溃与重复投递		分别在答案提交后、任务领取后、记忆提交后模拟 worker 退出；重复投递同一任务。无任务永久丢失；租约到期可恢复；重复任务不重复推进、不重复写入有效事实。核对答案/outbox、任务与记忆状态。
M10
超时及坏输出		注入模型超时、空输出、无效引用和无效结构化 facts。已完成的主回答不受影响；失败批次不推进对应游标；有限重试后可定位失败，不无界消耗费用。
M11
超过四块		准备需要至少六个 chunk 的未处理历史。先处理一个不超过四块且完整连续的前缀，成功推进到其末尾；后续任务继续处理剩余部分，不永久卡在“超限”。
M12
删除与隔离		准备不同 owner/env/agent/session 的相同问题；再于排队和执行中分别删除测试会话或使消息过期。只读写任务所属作用域；无串记忆。删除/过期校验阻止提交，不重建已删除数据。
M13
协议与兜底		构造含工具调用的超长历史，关键决定处于裁剪边界；另测当前问题本身超硬上限。无孤立工具消息；关键上下文无法保留时明确回查、同步兜底或澄清；当前输入超限仍按原规则拒绝，不能被裁剪偷偷放行。
M14
回归与负载		执行长会话配对样本、2/4 QPS 持续测试；停止请求后检查后台积压。达到第 05 节性能、资源、收敛与成本标准；保存全部失败，不以短会话性能替代长会话验收。
推广条件：先通过 M01–M14 的对应证据和性能对照，再扩大灰度。性能达标但关键事实、CAS、可靠投递或隔离失败，仍判定本次优化未通过。
